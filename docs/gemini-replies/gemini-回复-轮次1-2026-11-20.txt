先给出核心结论：你的怀疑中「免费个人团队受限导致无法正常在实体 Watch 上部署」的大方向有参考价值，但「因为 Profile 的 Platform 是 iOS 而非 watchOS、且免费账号无法签发 watchOS profile」这一核心归因存在前提误判。   
Open Source Alternatives

一、诊断纠偏与反证依据
1. 为什么不能把 Platform = iOS 当作根因？

Apple 机制本身就是 iOS 开发 Profile 覆盖 watchOS：在 Apple 开发者体系中，开发类 Provisioning Profile 本身就是 iOS App Development 类型，官方说明明确涵盖 iOS 和 watchOS 应用。本机出现 Platform = iOS 是常态，不是异常。

反证就在你自己的实测数据里：2.3 节已经证明，Xcode 已经为 com.dayecho.app.H98V6YZ5QL.watchkitapp 和 .watchkitapp.widget 生成了对应的 Profile（TimeToLive = 7），甚至里面还包含了 <key>com.apple.security.application-groups</key>。这说明「个人团队完全无法为 watchkitapp 生成 profile」的说法与实测矛盾。

2. 实测取证中值得警惕的其他线索

ProvisionedDevices 为空数组：你在 2.3 节提到每个 Profile 的 ProvisionedDevices 均为空数组。真机安装时，设备 UDID 是否被正确纳入/同步到 Watch 侧的 Profile 校验链，是真机签名安装失败的高频排查点（哪怕 iPhone 侧 devicectl 返回 0，Watch 侧仍可能因设备未列入 Profile、Watch 端 Profile 未同步或 Capability/Entitlements 校验未通过而拒绝安装）。

MIInstallerErrorDomain Code=111 的成因：在 MobileInstallation 链路中，Code=111 并不局限于「平台字段不匹配」单一原因，它通常与签名/Entitlements/Profile 校验失败或安装状态/设备授权不满足有关。仅凭 Platform = iOS 无法构成「充分且唯一」的因果证明。   
CSDN

IPA 目录结构细节（2.2 节）：你的结构树里出现了 Payload/DayEcho.app/PlugIns/DayEchoWidget.appex/DayEchoWatch.app/ 这一行（紧挨着 Payload/DayEcho.app/Watch/DayEchoWatch.app/）。虽然你 2.6 节已排除 Watch App 缺失，但建议核对实际 zip 归档中是否真的把 DayEchoWatch.app 误放进了 PlugIns/...appex/ 下——依附式 Watch App 应位于 Payload/DayEcho.app/Watch/DayEchoWatch.app（现代单 Target 布局）。

二、逐题回答（Q1 ~ Q5）
Q1：诊断是否成立？MIInstallerErrorDomain Code=111 还有哪些常见成因？

诊断不完全成立：Platform = iOS 不是错误，且 Watch 的两个 Bundle ID 已有 7 天 Profile。不能把「Platform 不是 watchOS」作为 Code=111 的直接充分原因。   
Open Source Alternatives

Code=111 的其他常见成因：

设备未在 Profile 的 ProvisionedDevices 中（尤其是 Watch 独立 UDID 未注册/未同步到 Profile）。   
CSDN

Entitlements 与 Profile 能力不匹配（例如 App Group、Keychain Sharing、Associated Domains 等在 Profile 中未授权或格式不符；虽然你看到 Profile 里有 application-groups，但仍需核对 Watch 端实际签名嵌入的 .mobileprovision 与 codesign -d --entitlements :- 是否完全一致）。

Watch 端配对同步/签名信任状态异常（iPhone 安装成功不代表 Watch 端 Profile/签名校验已通过，AppConduit 传输或 Watch 侧 MobileInstallation 校验失败也会触发安装中断）。

Q2：免费个人团队的硬限制与「App Group 架构不可行」是否属实？

免费个人团队的典型限制：

Provisioning Profile 有效期 7 天，到期需重新签名安装。   
Open Source Alternatives

无 Apple Distribution 证书（无法打 Ad Hoc / TestFlight / App Store 包）。

设备数量、App ID 数量及同时安装的免费签名 App 数量均有限制。

关于「无法创建/使用 App Groups」：

在 Apple Developer 后台，免费账号通常无法像付费账号那样在网页端完整管理 Capabilities/App Groups 资源；但在本地 Xcode 自动签名下，有时本地生成的临时 Profile 会写入 application-groups（正如你 2.3 节实测所见）。

但要注意：即使本地 Profile 里出现了 application-groups 字段，免费账号对受限 Capability/跨端共享的支持在真机安装与签名校验上依然存在不确定性/限制（付费 Apple Developer Program 才是官方完整支持 App Groups、CloudKit、后台能力及真机分发的前提）。

因此，如果 DayEcho 强依赖 App Group 做跨端账本共享，在免费个人团队下将其作为「可稳定落地的真机方案」风险极高、不可依赖；将其定性为「免费账号下真机路径受阻/不建议作为主力交付方案」是符合工程实际的。

Q3：不付费、不用第三方侧载、只走 Xcode 官方签名，是否有合法绕过路径？

直接走 Xcode 官方签名把 Watch App 装上实体 Apple Watch：没有可靠且合规的绕过路径。在官方签名体系下，真机安装必须满足证书、Profile、设备 UDID 与 Capability 校验，无法靠改字段或绕过签名校验强行装上实体表。

Xcode 登录同一免费账号，用 watchOS 模拟器能否作为替代交付路径？

可以作为「开发与功能验证/冻结基线」的替代交付形态（契合你第六节的取舍：模拟器门禁通过、实体机标为「未验证」）。

但要明确边界：模拟器不走真机 MobileInstallation 与真机 Profile 校验，也无法真实验证 BLE/Cloud 弱网、真机 WatchConnectivity 唤醒与后台调度、真机续航与性能。因此它只能证明「代码与共享逻辑在模拟环境跑通」，不能等同于「真机已交付」。

如果不用 App Group，改用其他共享机制能绕过免费账号限制吗？

不能绕过签名与真机部署限制本身。即使你把共享方式从 App Group 改成 WCSession 传数据或干脆不做跨端共享，只要 Watch App 仍要装上实体 Apple Watch，依然受限于免费账号的签名/Profile/设备限制与真机安装链路。

不过从工程解耦角度看：把「账本同步协议」抽象成独立接口（当前本地模拟/内存或 WCSession 实现，未来接 App Group / CloudKit），确实能让你的模拟器验证与后续付费真机联调互不阻塞。

Q5：Xcodeproj 生成工程（gen_xcodeproj.rb）该如何调整？watch_kit_target 与 intents_target 怎么办？

watch_target 与 watch_widget_target 挂上 Profile：

付费账号下创建好对应的 Development / Distribution Profile 后，在 gen_xcodeproj.rb 中为 watch_target 和 watch_widget_target 填入对应的 PROVISIONING_PROFILE_SPECIFIER（或在使用付费 Team 且 Xcode 自动管理时，确保 CODE_SIGN_STYLE = 'Automatic'、正确的 DEVELOPMENT_TEAM 与匹配的 Profile 名称一致；注意你贴出的代码片段里 apply_signing.call(ios_target, IOS_PROt, IOS_WIDGET_PROFILE) 还有拼写笔误，生成脚本时需一并修正）。

watch_kit_target（watchOS Framework）是否需要独立 Profile？

不需要独立 embedded.mobileprovision。Framework 本身不支持独立 Provisioning Profile，它由宿主 DayEchoWatch.app 在打包时嵌入并随宿主一起签名（使用相同的 DEVELOPMENT_TEAM 和 CODE_SIGN_IDENTITY）。

intents_target（AppIntents Extension）是否需要独立 Profile 与 Bundle ID 命名合理性：

如果 intents_target 是一个独立的 .appex扩展目标并参与真机签名打包，它需要独立的显式 App ID 和对应的 Provisioning Profile（不能用通配符应付带 Capability 的扩展）。

命名 com.dayecho.app.H98V6YZ5QL.intents（以及 com.dayecho.kit.watch.H98V6YZ5QL）：结构上是合法的反向域名格式，且在 watchOS 体系中 Watch App 的 Bundle ID 通常以宿主 App Bundle ID 为前缀（如 ...watchkitapp / ...watchkitapp.widget）。建议保持与现有 com.dayecho.app.H98V6YZ5QL.* 命名风格统一，避免出现多套前缀导致后台注册和 Capability 关联混乱。
