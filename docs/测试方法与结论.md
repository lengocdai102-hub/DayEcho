## 一、当前卡点（先说结论）

**代码侧没有已知卡点。** 4 个核心数据完整性 Bug 已修完并各有针对性单测，
74 条单测在 Mac 上真实跑通；CI 六轮失败的全部根因已定位并修复。

**★ 本轮工程防线的核心结论 ★**

CI 连续六轮编译失败，**每一轮 L1 单测（74 条）和 L2 语法检查都全绿**。
根因全部是「跨 module 引用」类问题 —— 本机没有 watchOS SDK，
这类错误只有真编译才能暴露。

为此新增两道本地检查，把这类遗漏从「等 3 分钟 CI」压到「本地 3 秒」：

| 新检查 | 抓什么 | 本轮实测抓到的真实 bug |
|---|---|---|
| `KitVisibilityCheck` | 缺 `import DayEchoKit` | `WatchTransferChannel.swift` / `WatchSessionCoordinator.swift` |
| `ProtocolConformanceCheck` | 协议成员漏实现 | `WatchTransferChannel` 缺 `deliversAcknowledgement` |

两道检查**都做了反向破坏性验证**（删掉实现 → 精准报错 → exit=1 → 恢复 → exit=0），
不是「写完就信」。

**★ 一条必须守住的传输安全底线 ★**

`WatchTransferChannel.deliversAcknowledgement` 必须是 `false` ——
真实 `WCSession.transferFile` 的 `didFinish` 只说明文件进了系统传输队列，
不代表手机端收到或校验通过。若错写成 `true`，段会在文件刚交给系统队列时
就被标记已验证并被保留策略清理 —— 手机端若最终没收到，这段录音**永久消失**。

## 二、测试方法

### 2.1 双 runner 架构：同一份测试代码，两个入口

本项目是 Swift Package，`DayEchoKit` 是纯逻辑层（不依赖 UIKit/WatchKit），
所以可以在 Mac 上直接跑。

**测试代码只有一份**，住在 `Sources/DayEchoTestCases/` 这个 library target 里：

| 文件 | 内容 |
|---|---|
| `Assert.swift` | 断言层（`checkEqual` / `checkNotNil` / `Suite.case_`） |
| `DayEchoKitTests.swift` | 存储 / 队列 / 校验 / 保留策略 |
| `DeviceReadinessTests.swift` | A–F 六组上机前验证套件 |
| `BoundaryTests.swift` | G1–G4 四组核心 Bug 边界套件 |

两个 runner 都依赖它：

| Runner | 入口 | 本机能用 | CI 能用 | 作用 |
|---|---|---|---|---|
| **自研 runner** | `swift run DayEchoTestRunner` | ✅ | ✅ | 主力。零依赖、单进程、退出码明确（0=全绿，1=有失败）、输出可读 |
| **XCTest** | `swift test` | ⚠️ 0 个测试（见下） | ✅ | 标准工具链入口 + 更细的失败定位（文件/行号/测试名） |

**★ 为什么测试代码要放 library 而不是 executable ★**

`executableTarget` 里的代码不能被别的 target import。
放成 library 才能两个 runner 共用同一份测试代码 ——
不会出现「自研 runner 过了但 XCTest 没测到」的漏网。

**★ 本机 XCTest framework 根本不存在 ★**

```bash
$ xcrun --find xctest
xcrun: error: unable to find utility "xctest", not a developer tool or in PATH
$ xcode-select -p
/Library/Developer/CommandLineTools
```

本机只有 Command Line Tools，没有完整 Xcode ⇒ XCTest 不存在。
所以 XCTest 桥接文件整体包在 `#if canImport(XCTest)` 里：

- **本机**：`swift test` exit=0（0 个测试被跳过），主力仍是自研 runner 的 74 条
- **CI**（有完整 Xcode）：XCTest 真跑，同一份测试代码

**★ 关键认知 ★**

```bash
  out=$(xcrun swiftc -parse "$f" 2>&1 | grep -E 'error:' | head -3)

echo '=== 语法检查完毕（无输出=全部通过） ==='
```

### 3.2 4 个 Bug 的修复 → 单测映射

#### Bug #1 时间戳计算错误

**旧算法**：`startedAt + (elapsed - segmentSeconds)`

**为什么错**：每一段的 `elapsed` 都 ≈ `segmentSeconds`，所以每一段算出的起点
都 ≈ `startedAt` ⇒ **所有段的时间戳挤在同一处**，iPhone 上时间线彻底失真。

**新算法**：`SegmentClock` 维护 `currentSegmentStart`，封段时取**重新观测的
`Date()`** 作为下一段起点，起点严格递增、不重叠、不漂移。

**单测**：
- `G1-1` 连续切段的时间戳连续且不重叠
- `G1-2` 误差不逐段累积（反推算法会平方级放大）
- `G1-3` `stop()` 尾段与前一段时间连续
- `A1` / `A2` 段起点独立记录、每段时间戳各不相同（回归测试，直接锁住旧 bug）

**方法要点**：为了让断言可计算，给 `SegmentWindow` 加了 `sealedAt`（封存时刻），
测试用 `sealedAt` **链式推导**下一段的 `now`，而不是手填常量——
手填常量容易写成「两段传同一个时刻」这种自欺欺人的断言。

#### Bug #2 落盘初始状态错误

**旧**：落盘默认 `.recorded` ⇒ 保留策略可能把还没传出去的录音删掉。

**新**：落盘默认 `.pending`；`applyRetention` **严格只扫 `.verified`**。
`.pending` / `.inFlight` / `.transferred`（待 ACK） / `.corrupted` 一律保留。

**单测**：
- `G2-1` 落盘默认态是 `.pending`（不是 `.verified`）
- `G2-2` 保留策略不删未传输 / 传输中 / 待 ACK / 损坏的段（**四种状态逐一验证**）
- `G2-3` 只有 `.verified` 才被保留策略清理
- `B1`–`B5` 旧套件覆盖同一条不变量的其他侧面

**方法要点**：新增了 `SegmentTransport.deliversAcknowledgement` 属性，
把「投递完成」和「已收到手机端 ACK」区分开。
不区分的话，`TransferCoordinator` 会把「文件传完但校验没过」的段误标成已验证 ——
这是 4 个 bug 里最隐蔽的一个，因为它只在「传输成功但校验失败」时触发。

#### Bug #3 `.inFlight` 死锁

**旧**：进程被杀后残留 `.inFlight`，重启后该段**永远不会被重新投递** ⇒ 录音静默丢失。
（这正是竞品 Auday 式卡死的机制。）

**新**：
- 冷启动恢复入口 `PendingTransferQueue.decode` 自动把残留 `.inFlight` 打回 `.pending`
- 运行期 `nextBatch` **绝不捞取**正在传输中的条目（防重复投递）

**单测**：
- `G3-1` 冷启动时残留 `inFlight` 全部重置为 `pending`
- `G3-2` 运行期 `nextBatch` 不捞取正在传输中的 `inFlight`
- `G3-3` 队列持久化往返后残留 `inFlight` 自动重置
- `G3-4` 重置**不影响**等待 ACK 的段（`.transferred` 不被误伤）

**方法要点**：G3-3 特别重要 —— 只测「内存里重置」不够，
必须测**序列化→反序列化**之后仍然重置，因为真实冷启动走的就是磁盘往返。

#### Bug #4 `stop()` 尾段丢失 + 双封存

**旧**：`stop()` 只停录音器，**最后一段从来没被封存过** ⇒ 每次停止录音，尾段（可能几十秒）直接丢失。

**新**：
- `stop()` 走 `RecordingSealer.endSessionAndSealTail()` 补封尾段
- 定时器切段和手动 stop() 都先问 sealer「轮得到你封吗」
- 撞车时**只有一方真正执行封存** ⇒ 既不双封存，也不丢尾段

**单测**：
- `G4-1` `stop()` 必须执行一次尾段封存
- `G4-2` 定时器先封存后 `stop()` 不双封存
- `G4-3` `stop()` 先封存后定时器不双封存
- `G4-4` 重复 `stop()` 尾段只封一次
- `G4-5` 定时器切段后可开始下一段并再次封存
- `G4-6` 定时器封段后 `stop()` 仍封存当前段（尾段不丢）

**方法要点**：G4-2 和 G4-3 是**一对** —— 必须双向都测。
只测「定时器先」会漏掉「stop 先」路径下的双封存。
G4-6 单独存在是因为「定时器刚切过段，用户马上停止」是最容易丢尾段的时序。

### 3.3 API 校正（4 处硬错误）

这 4 处曾是**编译期或运行时必炸**的错误，全部对照 Apple 官方文档修正：

| # | 错误用法 | 正确用法 | 后果 |
|---|---|---|---|
| 1 | `WCSessionTransfer` | `WCSessionFileTransfer` | 类型不存在，编译必炸 |
| 2 | `session(_:didReceive file:error:)` | `session(_:didReceive file:)` | 回调不触发，文件收不到 |
| 3 | `scheduleBackgroundRefresh(withIdentifier:)` 闭包 | `scheduleBackgroundRefresh(withPreferredDate:userInfo:)` + `WKApplicationDelegate` | 后台刷新永不触发 |
| 4 | `setTaskCompleted(success:)` | `setTaskCompletedWithSnapshot(false)` | 编译失败 |

**为什么这些没被单测抓到**：它们都在 `DayEchoWatchApp` / `DayEchoApp` 层，
依赖 `WatchKit` / `WatchConnectivity`，**不在 Mac SDK 里**，L1 单测层覆盖不到。
这正是 L2 语法检查和 L3 CI 编译存在的理由 —— 但要清楚：
**语法检查也抓不到这些**（它们语法是对的，是类型不存在）。
只有 L3 真编译才能抓到。所以 CI 必须过。

### 3.4 过程中被单测抓到的自身错误（诚实记录）

写测试的过程本身也暴露了 5 个我写错的地方，都已修正：

| # | 我犯的错 | 怎么被抓到的 | 修正 |
|---|---|---|---|
| 1 | `G1-2` 断言「误差不累积」时把「不累积」误算成「无误差」 | 断言失败，实测差值 1.8 ≠ 期望 2.0 | 改为验证差值**线性**增长（反推算法会平方级放大） |
| 2 | `G1-2` 基准算错：用了「最后一段起点」当基准 | 差值 -58.2，明显异常 | 改用「末段起点 - 会话起点」 |
| 3 | `G1-2` 期望切段次数多算 1 次 | 1.8 vs 2.0 | 末段起点之前只发生了 9 次切段，不是 10 次 |
| 4 | `A1`/`A2` 测试里 `now` 传了重复时刻 | 段起点相同 | 改用 `sealedAt` 链式推导 |
| 5 | `BridgeTransport` 没实现新协议属性 → **构建失败** | `swift build` 报 `error:`，跑的是旧二进制 | 补上 `deliversAcknowledgement` |

**第 5 条值得单独强调**：我一度以为「66/0 全绿」，实际是**构建失败后跑着旧二进制**。
判据是 `swift build` 的 `error:` 输出 —— 不能只看测试输出。
现在固定用 `swift build --product DayEchoTestRunner 2>&1 | grep 'error:'` 先确认构建成功，再跑二进制。

### 4.5b 根因四：新增语义时漏了枚举中间的 case（第 4 轮）

**原始错误**：

```
Sources/DayEchoWatchApp/WatchTransferChannel.swift:137:45:
error: type 'SegmentTransferResult' has no member 'transferred'
```

#### 事情是怎么发生的

第 3 轮修复时给 `SegmentTransport` 加了 `deliversAcknowledgement` 属性，
把真实通道 `WatchTransferChannel` 改成返回 `false` ——
含义是「`didFinish` 只说明文件进了系统传输队列，**不代表手机端校验通过**」。

但当时的 `WatchTransferChannel.send()` 直接返回了 `.transferred`，
而 `SegmentTransferResult` 枚举里只有这四个 case：

```swift
case verified       // 手机端已校验通过 ⇒ 可以移除
case hashMismatch   // 手机端算出的哈希对不上
case truncated      // 文件被截断
case rejected       // 手机端拒绝
```

**中间态「已交给系统队列、尚未收到 ACK」没有对应的 case。**

#### 为什么不能复用已有 case

| 如果返回 | 后果 |
|---|---|
| `.verified` | **误删未确认的录音** —— 文件刚进系统队列，手机端还没收到，条目就被移除了。手机端若最终没收到，这段录音永久消失。 |
| `.hashMismatch` / `.truncated` / `.rejected` | **触发无意义的重复传输** —— 走 `markFailed` 路径，每轮都重传，且 UI 上显示「传输失败」，而实际上文件已经交出去了。 |

两种都是「一个字节都不丢」的直接违背。

#### 正确解法：拆出 `.delivered`

```swift
public enum SegmentTransferResult: Equatable, Sendable {
    case verified
    case hashMismatch
    case truncated
    case rejected
    /// ★ 已交给系统传输队列，但尚未收到手机端 ACK ★
    case delivered

    /// 只有 `.verified` 才允许从队列移除
    public var isAcceptable: Bool { self == .verified }
    /// `.delivered` 是「投递完成」，不是失败
    public var isDeliveredOnly: Bool { self == .delivered }
    public var failureReason: String? {
        switch self {
        case .verified, .delivered: return nil
        case .hashMismatch: return "内容哈希不匹配"
        case .truncated: return "文件被截断"
        case .rejected: return "手机端拒绝"
        }
    }
}
```

配套改动：

| 文件 | 改动 |
|---|---|
| `TransferCoordinator.swift` | `pump()` 增加 `.delivered` 分支 → `queue.markTransferred(entry.id)`（**留在队列**），`report.delivered += 1` |
| `TransferCoordinator.swift` | `Report` 新增 `delivered` 计数 |
| `WatchTransferChannel.swift` | `send()` 返回 `.delivered` |

`TransferState.transferred` 这个队列状态**早就存在**，
`markTransferred` 也早就实现好了 ——
唯一缺的就是枚举里那个把两者连起来的 case。
**这就是典型的「新增语义但没走完全链路」。**

#### 为什么 66 条单测全绿却抓不到

**这是本轮最重要的教训。**

现有的 `FakeTransport` / `BridgeTransport` 全都是 `deliversAcknowledgement = true`
—— 它们在测试里**直接返回 `.verified`**，模拟了「ACK 已经回来」。

也就是说：

> **`deliversAcknowledgement == false` 这条分支，一行测试都没跑到过。**

而这条分支恰好是**真机上唯一会走的分支**。

#### 补的测试：H 组 8 条（`TransferSemanticsTests.swift`）

新建 `RealWorldTransport`（`deliversAcknowledgement = false`，返回 `.delivered`），
专门覆盖真实通道：

| 用例 | 钉死的不变量 |
|---|---|
| H1 | 投递无 ACK ⇒ 段**留在队列**，状态 `.transferred` |
| H2 | `.delivered.isAcceptable == false`（否则会误删） |
| H3 | 投递成功**不算失败**，不写 `lastError`，不触发重试 |
| H4 | ACK 到了才移除 —— 完整闭环（pump → apply(ack) → 队列清空） |
| H5 | 带 ACK 的通道投递即移除（两种通道差异钉死） |
| H6 | 载荷原样传出，不篡改 |
| H7 | `.transferred` 扛得住冷启动恢复（`resetInterruptedTransfers` 只重置 `.inFlight`） |
| H8 | ACK 的 sessionID / sequence / sha256 任一不符 ⇒ **绝不删数据** |

H4 的实现细节值得记一笔：
`evaluate(ack, against: entry)` 会逐项校验 `segmentID` / `sessionID` / `sequence` / `sha256`，
任何一项不符都返回 `.ignoreMismatch`，段**不会**被删。
所以 H4 里的 ACK 必须用**条目自己的** sessionID 和 sequence ——
随手编一个的话，测的就不是「正常 ACK → 删除」这条路径了。

H8 则是把这道闸门单独钉死：
**一条错配的 ACK 若能触发删除，可能删掉的是另一段的录音。**

#### 反向破坏性验证

改 `isAcceptable` 让 `.delivered` 也算可接受（模拟「误删」这个致命缺陷）：

```
通过 70 / 失败 4
  ✗ H2 .delivered 不是可接受结果
  ✗ H4 ACK 到了才移除（完整闭环）: ACK 前段还在 expected 0, got 1
  ✗ H1 投递无ACK ⇒ 段留在队列: 应算作 delivered（不是 verified） expected 0, got 1
  ✗ H3 投递成功不算失败: 条目还在 expected 0, got 1
```

注意 H1 / H3 里的 `expected 0, got 1` ——
**队列里段数从 1 变成 0，正是段被误删的直接证据。**
恢复原状后 74/74 全绿。

### 4.5c 根因五：Swift 6 并发检查 —— non-Sendable 类型跨隔离域传递（第 5 轮）

**原始错误**：

```
Sources/DayEchoWatchApp/WatchSessionCoordinator.swift:163:34:
error: sending 'didFinish' risks causing data races
note: task-isolated 'didFinish' is captured by a main actor-isolated closure.
main actor-isolated uses in closure may race against later nonisolated uses
```

#### 为什么第 4 轮没报这个错

**因为第 4 轮 `WatchTransferChannel.swift` 先编译失败，编译器根本没走到 `WatchSessionCoordinator.swift`。**

同一个 target 里，一个文件编译失败，后面的文件就不编译了 ——
所以前几轮的错误**遮住了**后面的错误。
这意味着：

> **前 4 轮修的每一个错，都可能还盖着下一个错。**
> 逐个修会一路挖一路，直到全通为止。

#### 根因

工程用的是 **Swift 6 + `SWIFT_STRICT_CONCURRENCY = complete`**（见 `legal/gen_xcodeproj.rb`）。
原来的代码是：

```swift
nonisolated func session(_ session: WCSession,
                         fileTransfer didFinish: WCSessionFileTransfer,
                         error: Error?) {
    Task { @MainActor in
        WatchRecorder.shared.handleTransferFinished(didFinish, error: error)
    }
}
```

`WCSessionFileTransfer` 是 **non-Sendable** 类型。
在 `nonisolated`（任务隔离）的回调里把它捕获进 **main actor 隔离**的闭包 ⇒ 数据竞争。

#### 修法（三处协同改动）

**① 只传 Sendable 的东西**

`transfer` 在这段代码里**只有一个用途** —— 算 `ObjectIdentifier` 当反查表的 key。
而 `ObjectIdentifier` 和 `URL` 都是 **Sendable**。

所以在 nonisolated 上下文里先算好，再传进去：

```swift
let transferID = ObjectIdentifier(didFinish)
let fileURL = didFinish.file
```

**② 通道提升为独立的 nonisolated 全局单例**

原来通道挂在 `WatchRecorder` 上，而 `WatchRecorder` 是 `@MainActor` 隔离的 ——
nonisolated 回调要访问它就得再跳一次 `Task { @MainActor }`，绕回原问题。

新增 `TransferChannelHolder`：

```swift
final class TransferChannelHolder: @unchecked Sendable {
    static let shared = TransferChannelHolder()
    private let channel: WatchTransferChannel
    private init() { /* 只创建一次，之后不再替换 */ }
    var current: WatchTransferChannel { channel }
}
```

它不受任何 actor 隔离，任意线程可直接访问；内部状态全由 `NSLock` 保护。
`WatchRecorder` 和 `WatchSessionCoordinator` 从它取**同一个实例**。

**③ 传输状态流转不再绕主线程**

通道内部全是 `NSLock` 保护的状态访问，**本来就不需要主线程**。
所以 delegate 回调里直接同步调用，只有 UI 刷新（待传计数、错误提示）才跳主线程：

```swift
// 传输状态流转：同步完成
TransferChannelHolder.shared.current.handleTransferFinished(
    transferID: transferID, fileURL: fileURL, error: error)

// UI 状态刷新：单独跳主线程
let errorDescription = error?.localizedDescription
Task { @MainActor in
    WatchRecorder.shared.handleTransferFinishedUI(errorDescription: errorDescription)
}
```

#### ★ 顺手修掉一个真实竞态 ★

改反查表时发现：`send()` 里原本是**先调用 `transferFile`、拿到对象后才登记**：

```swift
let transfer = WCSession.default.transferFile(fileURL, metadata: metadata)
transferToEntry[ObjectIdentifier(transfer)] = entryID   // ← 登记在调用之后
```

若 `didFinish` 回调在登记之前到达（传输极快，或系统立刻失败），
反查落空 → continuation 永不 `resume` → 传输永远挂着
→ 表现就是「录音一直卡在待同步」（Auday 最出名的差评场景）。

**修法**：主索引改用 `fileURL → entryID`。
文件 URL 是**我们自己算出来的**，`transferFile` 调用之前就有，
所以可以**提前登记**，这个窗口彻底消失：

```swift
// ★ 在 transferFile 调用之前登记 ★
transferLock.lock()
fileURLToEntry[fileURL] = entryID
transferLock.unlock()

let transfer = WCSession.default.transferFile(fileURL, metadata: metadata)
```

`ObjectIdentifier` 那张表保留作兜底。

#### ★ 本轮的结构性短板（诚实记录）★

**本机没有 watchOS SDK，也没有 Xcode.app**（只有 CommandLineTools），
所以：

- `swiftc -parse` 只能做**语法**检查 —— 能过；
- `swiftc -typecheck -target arm64-apple-watchos11.0` 直接失败
  （`unable to load standard library for target`）；
- 试过用 macOS SDK 代理验证 —— `WatchKit` 和 `WatchConnectivity`
  在 macOS SDK 里**都不存在**，代理验证走不通。

**⇒ Swift 6 的并发检查只有 CI 能验。**
本轮改动在本地只能做到「语法正确 + 逻辑审查 + 74 条单测不回归」，
并发正确性完全依赖 macos-15 runner。

### 4.5d 根因六：`WCSessionFileTransfer.file` 的类型是 `WCSessionFile`（第 6 轮）

**原始错误**：

```
Sources/DayEchoWatchApp/WatchSessionCoordinator.swift:204:46:
error: cannot convert value of type 'WCSessionFile' to expected argument type 'URL'
```

#### 根因

第 5 轮修并发时引入的新代码：

```swift
let fileURL = didFinish.file        // ❌ 类型是 WCSessionFile，不是 URL
```

`WCSessionFileTransfer.file` 返回的是 **`WCSessionFile`** 对象，
它才是「一个被传输的文件」的抽象；真正的路径在它的 `.fileURL` 属性上。

#### 修法

```swift
let fileURL = didFinish.file.fileURL
```

★ 为什么只取 `.fileURL`、不把 `WCSessionFile` 本身传出去 ★
—— `WCSessionFile` 是个 class，很可能不是 `Sendable`；
而 `URL` 是 `Sendable`。跨隔离域只传 `URL`，不传 `WCSessionFile` 本身。

#### ★ 顺带修掉的第二个隐患：反查表键的路径归一化 ★

第 5 轮把反查表主键改成了 `fileURL → entryID`，
但**登记用**的 URL 和**查找用**的 URL 来源不同：

| | 来源 | 可能是 |
|---|---|---|
| 登记 | `fileRoot.appendingPathComponent(fileName)`（我们自己算） | `/var/...` |
| 查找 | `didFinish.file.fileURL`（系统给的） | `/private/var/...` |

macOS/iOS 上 `/var` 是 `/private/var` 的软链接 —— **字面量不一致 ⇒ 反查 miss**
⇒ continuation 永不 `resume` ⇒ 传输永远挂着
⇒ 表现就是「录音一直卡在待同步」（Auday 最出名的差评场景）。

**修法：登记和查找都过同一个归一化函数。**

```swift
static func normalizedKey(_ url: URL) -> URL {
    url.standardizedFileURL.resolvingSymlinksInPath()
}
```

两个都要：
- `standardizedFileURL` —— 消掉 `./`、`../`、重复斜杠等**字面量差异**；
- `resolvingSymlinksInPath` —— 解析**软链接**（`/var` → `/private/var`）。

只用 `standardizedFileURL` 解决不了软链接；
只用 `resolvingSymlinksInPath` 解决不了 `./` `../` 的字面量差异。

#### ★★ 但光有归一化键还不够 ★★

`resolvingSymlinksInPath` 对**不存在**的路径**不解析软链接**。
而登记和查找发生在不同时刻：

- 登记时：文件刚写完、还在 ⇒ 解析成功 ⇒ 键是 `/private/var/...`
- 查找时：文件可能已被移走/清理 ⇒ 解析不出 ⇒ 键又变回 `/var/...`

⇒ 光靠归一化键仍可能对不上。

**最终解法：两种键都登记，查找时两种都试。**

```swift
static func normalizedKey(_ url: URL) -> URL {
    url.standardizedFileURL.resolvingSymlinksInPath()
}

/// 只做字面量规范化的键（不解析软链接）
static func literalKey(_ url: URL) -> URL {
    url.standardizedFileURL
}

// 登记
fileURLToEntry[Self.normalizedKey(fileURL)] = entryID
fileURLToEntry[Self.literalKey(fileURL)] = entryID

// 查找
entryID = fileURLToEntry.removeValue(forKey: Self.normalizedKey(fileURL))
if entryID == nil {
    entryID = fileURLToEntry.removeValue(forKey: Self.literalKey(fileURL))
}
```

命中任一即可 —— **不依赖「文件当时在不在」**，无条件正确。
最后按 `entryID` 把另一张表的残留一并清掉，避免双键残留泄漏。

### 4.6 根因三的补充：新增 KitVisibilityCheck 防回退

既然这类错误「本地永远抓不到」，就写一个能抓的静态检查：
`Sources/KitVisibilityCheck/main.swift`。

逻辑：解析出 DayEchoKit 的全部 `public` 顶层符号，扫每个引用方的文件 ——
如果文件里用到了 Kit 符号却没有 `import DayEchoKit`，就报错。

```bash
swift run KitVisibilityCheck
# ✅ 通过 6 个文件 —— 没有缺 import 的
# exit=0
```

**接进 CI 的第 1 个检查位**（真编译在第 6 步）：
缺 import 在 **3 秒内**暴露，而不是 2 分钟后。

**反向破坏性验证**（不是「写完就信」）：

```bash
# 临时删掉 WatchTransferChannel.swift 的 import
./.build/debug/KitVisibilityCheck
# ✗ Sources/DayEchoWatchApp/WatchTransferChannel.swift
#   用了 Kit 符号（SegmentTransferResult, SegmentTransport, TransferPayload）
#   但**没有 import DayEchoKit**
# exit=1
```

**写这个检查器时自己踩的 3 个坑**（都修了，诚实记录）：

| # | 坑 | 症状 | 修法 |
|---|---|---|---|
| 1 | 符号提取没切冒号 | `public protocol Foo: AnyObject` 被解析成 `"Foo:"`，导致所有协议/类都匹配不上 | 切掉 `:` 和 `<T>` |
| 2 | `stripComments` 逐字符状态机在行注释边界漏状态转移 | 注释里的符号名被当代码，误报一堆 | 改成逐行 + 块注释开关 |
| 3 | `hasImport` 用 `text.contains("import DayEchoKit")` | 注释里写「★ 必须 import DayEchoKit ★」也算匹配 ⇒ **假阴性**（缺 import 反而报「已 import」） | 改成行首正则 `(?m)^[ \t]*import[ \t]+DayEchoKit[ \t]*$` |

第 3 个坑最阴险：**它让检查器在最需要的时候失效**。
如果没做反向验证，这个检查器会一直「全绿」，而真实问题还在。

### 4.7 根因三b：协议成员漏实现（第 3 轮）

```
error: type 'WatchTransferChannel' does not conform to protocol 'SegmentTransport'
note: add stubs for conformance
note: protocol requires property 'deliversAcknowledgement' with type 'Bool'
```

**根因**：我给 `SegmentTransport` 协议新增了 `deliversAcknowledgement` 属性。
测试里的 `FakeTransport` 顺手补了（**同 module，编译器当场提示**），
但真实实现 `WatchTransferChannel` 在 **watchOS target** 里 ——
本机没有 watchOS SDK，编译不到 ⇒ 只有 CI 能发现。

**修法**：

```swift
// Sources/DayEchoWatchApp/WatchTransferChannel.swift
public var deliversAcknowledgement: Bool { false }
```

**★ 为什么必须是 `false`（这是数据安全的底线）★**

`WCSession.transferFile` 的 `didFinish` 只说明**文件已交给系统传输队列**，
不代表手机端收到、更不代表校验通过。
手机端的验收结论要等**另一个方向**的 ACK 回来才知道。

所以这个通道返回 `false` ——
`send()` 成功只让段流转到 `.transferred`，
必须等 `apply(acknowledgement:)` 收到手机端校验通过的 ACK 才流转到 `.verified`，
此时才允许从待传队列移除。

**如果这里错写成 `true`**，段会在文件刚交给系统队列时就被标记成已验证，
随后被保留策略清理掉 —— 手机端若最终没收到，这段录音就**永久消失**。
这与 DayEcho「一个字节都不丢」的承诺直接冲突。

### 4.8 根因三b 的补充：新增 ProtocolConformanceCheck 防回退

`Sources/ProtocolConformanceCheck/main.swift`：
从 Kit 的协议定义里解析出所有**没有 default 实现**的成员，
逐个核对每个实现该协议的类型是否真的提供了它。

```bash
swift run ProtocolConformanceCheck
# Kit 协议 SegmentTransport
# 协议成员 2 个（其中必需 2 个）
#   ✓ Sources/DayEchoWatchApp/WatchTransferChannel.swift — WatchTransferChannel (SegmentTransport)
# ✅ 全部通过
# exit=0
```

**反向破坏性验证**：

```bash
# 临时删掉 deliversAcknowledgement 实现
./.build/debug/ProtocolConformanceCheck
#   ✗ Sources/DayEchoWatchApp/WatchTransferChannel.swift
#     — WatchTransferChannel 缺 var deliversAcknowledgement
# exit=1
```

**★ 检查器自己踩的坑（已修）★**

判据一开始写成「协议成员行里出现 `{` ⇒ 有 default 实现」，
结果 `var x: Bool { get }` 被误判成有 default 实现 ——
但 `{ get }` 是**访问器说明符**，实现方**仍然必须**提供 `x`。
（CI 真实报的就是这个成员。）

改法：看 `{` 后面是不是 `get` / `get set` —— 是的话就不是 default 实现。
修好后「必需成员」从 1 个变成 2 个，判据才对上。

### 4.10 顺带修掉的两个既有缺陷

这两个不是本轮 CI 报错，是做本地全量检查时暴露的：

**① `swift test` 完全不能用**

**★ 有一个反直觉的结论值得单独说 ★**

CI 连续六轮失败，**每一轮都是新的根因**，而且每一轮 L1 单测（74 条）和 L2 语法检查**全绿**。
这说明：

> **「本地全绿」不等于「能编译」。**
> 真正能抓跨 module 问题的，只有真编译。

而且 —— **前一轮修的错会遮住后一轮的错**：
第 4 轮 `WatchTransferChannel.swift` 编译失败，编译器就没走到 `WatchSessionCoordinator.swift`，
所以第 5 轮的并发错误此前一直藏着。
这意味着前 4 轮每修一个错，很可能只是**掀开了下一层**。
只有跑到全通为止。

所以本轮加的 L0a / L0b 两道检查不是锦上添花 ——
它们是在补「本机完全没有 watchOS SDK」这个硬约束留下的洞。
但也必须诚实：**L0a / L0b 只能抓语义遗漏，抓不到真 SDK 的行为差异**
（比如某个 API 在 iOS 17 能用、iOS 18 改了行为）。
那一层永远只有 CI 和真机能覆盖。
