## 0. 本版定位与对 v2 的继承

v2 是「论证什么值得做」，本版是「接下来 15 个工作日具体做什么」。

**唯一目标**：产出你自己每天上班、接电话时真正愿意用的 V1 最小闭环。

**成功定义（V1 完成的唯一判据）**：

> 你在 5 个工作日里，戴着 Watch 正常使用 DayEcho，**至少 2 次本来要忘掉的日程被系统提醒成功兜住**，且**没有一次你忍不住忽略的废话提醒**。

达不到这条，其余一律不算完成。

**对 v2 的继承**：v2 的「后悔药两层架构」「状态法取证」「App Store 雷区」结论全部保留，但**移出当前 Sprint**（见 §1 裁剪表），上架前再补。

## 1. 战略裁剪：移出当前 Sprint 的重资产

在写任何新代码之前，以下模块标记为 **v2.0**，本 Sprint 不碰：

| 移出项 | 原设想 | 替代方案（本 Sprint 做） | 移出理由 |
|---|---|---|---|
| **Watch 全天 8–12h 常开录音** | 全天无脑录音，靠后台刷新维持 | **表盘一键抓拍**：单次 60–120s 自动封条，支持手动延长 | 电池 + 后台挂起雷区；且「零操作被动捕获」本身与产品核心假设冲突（见 v2 §1.3） |
| **端侧大模型（Apple Intelligence）** | iOS 26 新框架 + M 芯片 | **`SFSpeechRecognizer` 端侧识别** + 现有 `TimeExpressionExtractor` 规则层 + `NLTagger` 分词 | 本机 Intel Mac；且大模型是「锦上添花」，不是链路必需 |
| **残障合规标签 / 51 州法律弹窗 / 照护者多端闭环** | 完整合规 UI + 远程照护 | V1 只做 TestFlight 内测，**合规 UI 全部延后到上架前** | 内测阶段无需面对审核；且这正是 v2 认定「实现方式未定」的部分 |
| **端侧模型层抽取（P0）** | v2 里是 P0-3 | 降为 **P1**，不阻塞 MVP | 规则层 + SFSpeechRecognizer 已能覆盖主路径 |
| **全天录音 8h 压测协议** | v2 里的 P-1 生死线 | 降为 P2（因主路径已改，不再是生死线） | 前提被裁掉，验证对象随之消失 |

> ★ **注意这与 v2 的关系**：v2 把「全天录音可行性」列为 P-1 生死线，是因为当时它还在主路径上。
> Gemini 第三轮的建议把它移出主路径 ⇒ **生死线随之转移**：新的生死线是
> 「**表盘一键抓拍 → 15 秒内回传 → 端侧转写 → 候选生成**」这条链路能不能在真机上跑通。

## 2. 官方 API 取证结论（本方案的硬前置）

> ★ 全部经 `developer.apple.com/tutorials/data/documentation/<path>.json` 实测。
> 200 = 符号存在，404 = 从未存在。

### 2.1 方案中 API 名的核实结果

| Gemini 方案中的写法 | 核实结果 | 说明 |
|---|---|---|
| `SFSpeechRecognizer` + `requiresOnDeviceRecognition = true` | ✅ **正确**，但属性在 **`SFSpeechRecognitionRequest`** 上，不在 `SFSpeechRecognizer` 上 | 正确用法：<br>`let req = SFSpeechRecognitionRequest();`<br>`req.requiresOnDeviceRecognition = true` |

| `SFSpeechRecognizer` 可用平台 | ⚠️ **iOS / iPadOS / Mac Catalyst / macOS / visionOS —— 不含 watchOS** | ⇒ **转写必须放在 iPhone 侧**，Watch 只录音不转写。这与方案「在 iPhone 端转写」一致 |

| Watch 表盘按钮 | ⚠️ **`WKComplication` 404（WidgetKit 下也无）**；`CLKComplication` 存在但已被 WidgetKit 取代 | **现代做法：WidgetKit `accessoryCircular` / `accessoryCorner` / `accessoryRectangular` 家族**（已实测存在） |
| `AppIntents` | ✅ `AppIntent` + `perform()` 存在（iOS 16+） | |
| `NLTagger` | ✅ 存在（iOS 12+） | |
| `WCSession` / `WKExtensionDelegate` | ✅ 存在 | |
| `WKApplicationRefreshBackgroundTask` | ✅ 存在（但本方案不再依赖后台录音，意义降为可选） | |

### 2.2 由此产生的三处方案修正

**① 转写位置** —— 已在 iPhone 侧 ✅ 无需修改。

**② Watch 表盘入口** —— 不用 `WKComplication`（该符号在 WidgetKit 下不存在），
改用 **WidgetKit accessory 家族**：新增 `DayEchoCaptureWidget`，
声明 `accessoryCircular`（圆形单按钮），`AppIntent` 触发录音。

**③ 「通话录音在 Notes 中」的路径** —— Gemini 方案 2.4 说
「抓取 iOS 18.1+ 自带通话录音在 Notes 中的最新转写文本」。
★ **本机无法核实这条路径是否公开可用**（属「未取到」项，见 §7）。
方案落地改为：**App Intent 接收用户主动提供的文本**（从快捷指令的
「共享文本」输入喂入），不依赖系统通话录音自动落 Notes。
⇒ 这是**用户主动投递（L2）**通道，v2 已确认它是 iOS 唯一合法的外部文本入口。

## 3. 三源归一的数据入口模型（阶段 1.2 交付物）

```
┌─────────────────────────────────────────────────────────┐
│ 三个输入源（都只产出「文本 + 来源 + 时刻」）              │
├──────────────┬──────────────┬───────────────────────────┤
│ Watch 抓拍   │ Share 扩展   │ App Intent（快捷指令）      │
│ 音频→转写    │ 选中文本     │ 共享文本                   │
└──────┬───────┴──────┬───────┴──────────┬────────────────┘
       │              │                  │
       └──────────────┴──────────────────┘
                      ↓
        IngestedTextEntry（统一封装）
        ├─ source: IngestionSource
        ├─ text: String
        ├─ occurredAt: Date
        ├─ audioRef: String?（仅 Watch）
        └─ rawPayload: Data?
                      ↓
        时间表达式抽取（TimeExpressionExtractor）
                      ↓
              LifeEvent（Timeline）
                      ↓
        候选构建（分源策略，见 §6.1）
                      ↓
        ┌─────────────┴─────────────┐
        ↓                            ↓
   第一层：高确定性              第二层：静默
   → 弹窗 → 用户确认            → 只进时间轴
   → 写入系统提醒               → 事后可检索
   （EventKitReminderWriter）    （不打扰，不丢）
```

**关键设计约束**（Gemini 方案 1.2 的「走完全同一套抽取与时间轴存储逻辑」）：

- 三个源**共用同一个抽取入口** ⇒ 不允许任何源绕过规则层直接写 EventKit
- 三个源**在分档策略上可以不同**（外部文本信噪比高，Watch 严格），
  但**分档必须在候选构建阶段用 `source` 显式表达**，不能靠隐式默认值

### 4.2 任务 1.2 —— 统一输入模型

**动作**（在 `Sources/DayEchoKit/Models.swift` 新增）：

```swift
/// 输入来源 —— 决定候选过滤策略与提示文案
public enum IngestionSource: String, Codable, Sendable, CaseIterable {
    /// Watch 表盘一键抓拍（音频 → 端侧转写）
    case watchCapture
    /// Share Extension 选中的外部文本（邮件/聊天）
    case shareExtension
    /// App Intent（快捷指令）喂入的文本
    case shortcutIntent
}

/// 统一文本入口 —— 所有外部文本进系统的唯一载体
public struct IngestedTextEntry: Codable, Sendable, Hashable {
    public let id: UUID
    public let source: IngestionSource
    public let text: String
    /// 内容产生的时刻（不是进入系统的时刻）

    /// 仅 watchCapture 有：对应的录音段标识
    public let audioRef: String?
    /// 原始载荷（Share 扩展传原文、Watch 传文件名）
    public let rawPayload: Data?

    public init(...)
}
```

**验收标准**：

- `ReminderCandidateBuilder` 的入口改为接收 `IngestedTextEntry`（而非裸 String）
- 旧调用点全部迁移，**编译无警告**

### 5.1 任务 2.1 —— Watch 交互重构：表盘一键抓拍

**保留**：`RecordingStore`（60s 分段）、`RecordingSealer`（封条 + SHA-256）、

**新交互**（对应 Gemini 的「屏幕只留一个超大『停止并发送』按钮与呼吸灯指示」）：

| 元素 | 规格 |
|---|---|
| 表盘入口 | WidgetKit `accessoryCircular` 家族，点击 = 启动抓拍（AppIntent） |
| 默认时长 | **120 秒自动封条**（方案说 60–120s，取上限以覆盖「老板交待一段话」） |
| 可延长 | 录音中点「+30s」按钮，最多 3 次 ⇒ 上限 210s |

| 状态指示 | 录音中 = 红色呼吸灯（`TimelineView` + `opacity` 动画） |

### 5.2 任务 2.2 —— iPhone 端端侧转写（P0-3）

**位置**：`Sources/DayEchoApp/`（新建 `SpeechTranscriber.swift`）

**实现要点**（用已核实的官方 API）：

```swift
// 1) 预检：这台设备/这个语言是否支持离线识别
guard SFSpeechRecognizer.supportsOnDeviceRecognition else { /* 降级为仅存音频 */ }

// 2) 权限
SFSpeechRecognizer.requestAuthorization { ... }

// 3) 强制离线
let req = SFSpeechRecognitionRequest()
req.requiresOnDeviceRecognition = true     // ← 属性在 Request 上，不在 Recognizer 上
req.shouldReportPartialResults = false      // 分段封条后才转写，只要最终结果

// 4) 识别
let recognizer = SFSpeechRecognizer(locale: Locale(identifier: "en-US"))
recognizer.recognitionTask(with: req) { result, error in ... }
```

**分段与时间戳**：每个 `.sealed` 分段独立转写，
`occurredAt` = 分段起始时间 + 分段内偏移（用 `SegmentClock` 现有的窗口逻辑）。

**验收标准**：
- 飞行模式 + `requiresOnDeviceRecognition = true` 下，**3 秒内**产出文字并挂上时间轴
- 转写失败（不支持离线 / 无权限）⇒ **降级为只存音频，不丢数据**，并在时间轴标记「未转写」

## 6. 阶段 3：抽取 → 确认 → 系统提醒（第 7–11 天）

### 6.1 任务 3.1 —— 分源候选过滤规则

**修改** `Sources/DayEchoKit/ReminderCandidate.swift`：

| 来源 | 第一人称自我指令词要求 | 附加条件 |
|---|---|---|
| `.watchCapture` | **必须满足**（严格） | 现有规则不变 |
| `.shareExtension` | **放宽**：只要「未来时间表达式 + 动词短语」即生成候选 | 需 `sourceQuote` 非空 |
| `.shortcutIntent` | **放宽**：同 `.shareExtension` | 需 `sourceQuote` 非空 |

**为什么可以放宽**：外部文本是用户**主动挑出来交给 App 的**，
信噪比远高于被动录音；方案原话「不被词表误杀」。

**但仍不可自动写入**（保持 v2 的误报防护）：

```
needsConfirmation 恒为 true（第一层也需要用户点一下「写入提醒」）
```

★ **这是对 Gemini 方案的一处收紧**：方案 3.1 说「生成候选」，
没说可自动写入。v2 已确立「误报比漏报更危险」⇒ **任何来源都不得绕过用户确认直接写 EventKit**。

**分档（后悔药两层架构）**：

```swift
public enum CandidateTier: String, Sendable, Codable {
    /// 高确定性 → 主动弹窗 + 用户确认 → 写入系统提醒
    case active
    /// 静默 → 只进时间轴，事后可检索
    case silent
}
```

分档判据（在 `ReminderCandidateBuilder` 内）：
- 满足「强时间锚点 + 强自我指令」双条件 → `.active`
- 仅命中时间表达式（缺自我指令词）→ `.silent`
- 时间表达式缺失或已过期 → **不生成候选**

**验收标准**：
- 「明天上午十点把表发我」（Watch 转写，来源是老板说的，**非**用户本人）
  ⇒ **不生成第一层候选**（不含第一人称自我指令）⇒ 归入第二层静默
- 邮件里「周五下午3点开会」⇒ 生成第一层候选（外部主动投递）
- 「下月15日参加婚礼」⇒ 生成第一层候选

**路径 A —— 你自己有付费 Apple Developer 账号**

- 成本：约 $1–3/小时

⚠️ **两条路径都绕不开「需要一个可签名的 Apple ID / 开发者账号」**，
这是 Apple 平台硬约束，不是工程问题。
