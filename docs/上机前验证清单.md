### ★★★ 必须先知道的两个真实缺口 ★★★

**缺口 A：手机端「发 ACK」这一环还没实现（影响面大，但数据不丢）**

协议层是完整的 —— `SegmentAcknowledgement`（含 segmentID / sessionID / sequence /

一致性校验、Watch 侧的 `.transferred → .verified` 流转逻辑，**全都写好了，且 8 条单测全过**。

**但没有一行生产代码真正发送或接收 ACK**：
- iPhone 侧 `PhoneReceiveChannel` 里没有任何 `transferUserInfo` / `sendMessage` 发送 ACK 的代码；
- Watch 侧也没有 `didReceiveUserInfo` / `didReceiveMessage` 里解析 ACK 的代码。

**实际后果（务必理解，不要误判）**：
段会停在 `.transferred` 状态，**永远不流转到 `.verified`**。

| 影响 | 结论 |
|---|---|
| 录音会丢吗？ | **不会。** 恰恰相反 —— 因为永不 `.verified`，保留策略永远不会删它 |

| 保留策略 | **形同虚设。** 步骤 6 的「只清已确认段」目前实际清不掉任何东西 |
| 第 4 轮设计的状态机 | **闭环没接上。** 状态机本身对，但两端没连线 |

### 1.4 4 个 Bug 的修复点

**Bug #1 时间戳计算**
- 旧：`startedAt + (elapsed - segmentSeconds)` → 每段 elapsed 都 ≈ segmentSeconds，
  于是**所有段的时间戳挤在同一处**，iPhone 上时间线彻底失真。
- 新：段起点 = 上一段的**封存时刻**（重新观测的 `Date()`），由 `SegmentClock` 维护，
  不重叠、不漂移、误差不随段数放大。
- 单测：`G1-1`（起点严格递增）、`G1-2`（差值线性增长，反推算法会平方级累积）。

**Bug #2 初始状态**
- 旧：落盘默认 `.recorded` → 保留策略可能把还没传出去的录音删掉。
- 新：默认 `.pending`；保留策略**只清 `.verified`**，
  `.pending` / `.inFlight` / `.transferred`（待 ACK） / `.corrupted` 一律保留。
- 单测：`G2-1`（默认态断言）、`G2-2`（四种状态都不被删）、`G2-3`（只有 verified 被清）。

**Bug #3 `.inFlight` 死锁**
- 旧：进程被杀后残留 `.inFlight`，重启后该段永远不会被重新投递 ⇒ 录音静默丢失
  （这正是 Auday 式卡死的机制）。
- 新：冷启动恢复入口（`PendingTransferQueue.decode`）自动把残留 `.inFlight` 打回 `.pending`；
  **运行期** `nextBatch` 绝不捞取正在传输中的条目（防重复投递）。
- 单测：`G3-1`（重置数量）、`G3-2`（运行期不捞）、`G3-3`（持久化往返后自动重置）、
  `G3-4`（不影响待 ACK 的段）。

**Bug #4 `stop()` 尾段丢失**
- 旧：`stop()` 只停录音器，**最后一段从来没被封存过** —— 每次停止录音，尾段直接丢失。
- 新：`stop()` 走 `RecordingSealer.endSessionAndSealTail()` 补封尾段；
  定时器切段与手动 stop() 都先问 sealer「轮得到你封吗」，
  撞车时只有一方真正封存 ⇒ 既不双封存，也不丢尾段。
- 单测：`G4-1`~`G4-6`（含「定时器先封后 stop() 不双封」「stop() 先封后定时器不双封」
  「定时器封段后 stop() 仍封尾段」三个关键路径）。

### 步骤 2：分段时间戳连续性（10 分钟）★ 验 Bug #1

1. 手表上连续录 **5 分钟以上**（至少 5 段）。
2. 停止录音。
3. iPhone 端查看时间线/段列表。

### 步骤 3：停止录音后尾段存在（3 分钟）★ 验 Bug #4

1. 录音 **2 分 30 秒**（录到第 2 段中途）。
2. 停止录音。
3. 立刻看 iPhone 端段列表。

**通过判据**：
- 段数 = 3（定时器封的 60 秒 + 60 秒 + stop 封的 30 秒尾段）
- 尾段时长 ≈ 30 秒，**不是 0**、**不是 60 秒**
- 段序号连续：0 → 1 → 2（无跳号）
- iPhone 端显示的**总时长 ≈ 150 秒**（与实际录音时长一致，不是只算满段）

**失败定位**：
- 尾段丢失（只有 2 段）⇒ `stop()` 未走 `finalizeTailSegment`，
  检查 `sealer.endSessionAndSealTail()` 的返回值
- 尾段重复（出现 2 个 30 秒段）⇒ 双封存，检查 `finalizeSegment` 是否也封了一遍
- 总时长偏小 ⇒ `SegmentClock.totalRecorded` 的累加逻辑被破坏

### 步骤 4：断连与重连补传（10 分钟）★ 验 Bug #3

1. 录音 3 分钟（保证有段待传）。
2. **关掉手表蓝牙**（或让 iPhone 远离 1 米+开飞行模式）。
3. 继续录 2 分钟。
4. 恢复蓝牙连接，等 2 分钟。

**通过判据**：
- 断连期间录的段**一条都不丢**，恢复连接后全部补传
- iPhone 端段总数 = 断连前 + 断连期间，无缺失
- 无重复音频（同一段不出现两次）

**失败定位**：
- 段卡在手表不传 ⇒ 检查 `WatchTransferChannel` 的 `transferFile` 是否在
  `activationState == .activated` 时才调用
- 重复音频 ⇒ 运行期 `nextBatch` 捞取了 `.inFlight` 条目，查 `G3-2` 逻辑是否被绕过

### 步骤 5：手表重启后恢复（5 分钟）★ 验 Bug #3 冷启动

### 步骤 7：★ `.delivered` 未确认前绝不删除（新防线 1）★

> 验第 4 轮引入的 `.delivered` 中间态。这是**整个数据安全设计的核心**。

**原理回顾**：

`WCSession.transferFile` 的 `didFinish` 成功，只说明**文件进了系统传输队列**，
不代表手机收到了，更不代表手机校验通过。以下情况 `didFinish` **依然会成功**：

- 手机 App 被删了；
- 手机拒绝接收（空间不足 / 未信任 / 版本不兼容）；
- 文件在传输途中被损坏。

所以段状态机是两级确认：

```
.pending ──didFinish 成功──> .transferred ──手机端 ACK 校验通过──> .verified ──> 才可删除
                                  │
                                  └──★ 在这里绝不能删 ★
```

**验证步骤**：

1. 手表上录 **2 分钟**（产生 2 段）。
2. 保持手表与 iPhone 正常连接，等段传完。
3. **在 iPhone 端删掉 DayEcho App**（或让 iPhone 长时间离线）。
4. 继续在手表上录 **2 分钟**。
5. 回到手表端查段状态。

**通过判据**：

- 已 `didFinish` 但**没收到手机 ACK** 的段，**仍然留在待传队列里，一条都没被删**；
- 手表上能明确看到「已投递但未确认」这类中间状态（或至少：段还在、文件还在）；
- 手表存储占用**只增不减**，不会因为「传完了」就自动清空。

**失败定位**（任一条出现即为严重 bug）：

| 现象 | 根因 |
|---|---|
| `didFinish` 后段立即消失 | `deliversAcknowledgement` 被错写成 `true` |
| 段被标成 `.failed` 并自动重传 | `.delivered` 被误映射成失败态（会触发无意义的重复传输） |
| 段被标成 `.verified` | `.delivered` 被误映射成已确认（**最严重，等于误删**） |

**对照代码**：`Sources/DayEchoKit/TransferCoordinator.swift` 的 `isAcceptable`
（**只应认 `.verified`**）、`Sources/DayEchoWatchApp/WatchTransferChannel.swift` 的
`deliversAcknowledgement`（**必须是 `false`**）。
**对应单测**：H1 / H2 / H3 / H4（`.delivered` 不是 acceptable、
不是 failed、不进队列清理、ACK 前仍在队列）。

### 步骤 8：★ `/var` 双键反查不悬挂（新防线 2）★

> 验第 6 轮引入的双键反查机制。

**原理回顾**：

反查表主键是 `fileURL → entryID`。但登记用的 URL 和查找用的 URL 来源不同：

| 时机 | URL 来源 | 可能得到 |
|---|---|---|
| 登记（调用 `transferFile` **之前**） | `fileRoot.appendingPathComponent(...)`（我们自己算） | `/var/...` |
| 查找（`didFinish` 回调里） | `didFinish.file.fileURL`（系统给的） | `/private/var/...` |

macOS / iOS 上 `/var` 是 `/private/var` 的软链接 ⇒ 字面量不一致 ⇒ **反查 miss**
⇒ continuation 永不 resume ⇒ **传输永远挂着**（表现：录音一直卡在「待同步」，
`didFinish` 明明成功了但队列不动）。

**只上 `standardizedFileURL` 不够** —— `resolvingSymlinksInPath` 对
**不存在**的路径不解析软链接。登记时文件刚写完还在（解析出 `/private/var/...`），
查找时文件可能已被移走（解析不出，又变回 `/var/...`）⇒ 仍可能对不上。

**最终解法**：**两种键都登记**（normalized = standardized + resolvingSymlinks，
literal = standardized），**查找时两种都试**，命中任一即可。
不依赖「文件当时在不在」，无条件正确。

**验证步骤**：

1. 手表上录 **3 分钟**。
2. 等所有段 `didFinish`（注意观察 UI 上有没有一直转圈的「传输中」）。
3. **重点**：在传输进行中，让 iPhone 短暂断连（开飞行模式 10 秒再关），
   制造「文件在系统队列里、但回调时文件可能已被移走」的时机。
4. 记录每段的最终状态和传输耗时。

**通过判据**：

- **没有任何段卡在「传输中 / 等待中」超过 2 分钟**（卡住 ⇒ 反查 miss）；
- 所有 `didFinish` 过的段都能从「传输中」流转出去；
- 反复断连 3～5 次，**每次都不出现永久卡住的段**。

**失败定位**：

| 现象 | 根因 |
|---|---|
| 段永远卡在「传输中」，`didFinish` 明明成功过 | 反查 miss ⇒ 检查 `normalizedKey` / `literalKey` 是否**登记和查找两侧都用了** |
| 只有部分段卡住 | 只登记了一种键，或查找时只试了一种 |
| 传输卡住时 `continuation` 悬挂 | `fileURLToEntry` 查询失败后没有走 `transferToEntry` 兜底 |

**对照代码**：`Sources/DayEchoWatchApp/WatchTransferChannel.swift` 的
`normalizedKey` / `literalKey` / `handleTransferFinished`。
**注意**：这个 bug 的表现和「文件根本没传出去」很像 ——
区分方法是看 `didFinish` 有没有触发过（真机日志里会有记录）。

### 步骤 9：★ metadata 缺失转损坏隔离（新防线 3）★

> 验第 7 轮引入的保守处理。

**原理回顾**：

`WCSessionFile.metadata` 的类型是 **`[String: Any]?`**（可选字典）——
**系统不保证一定带元数据**。元数据里装着这一段的身份信息：

```
fileName / sha256 / byteCount / sessionID / sequence / startedAt / endedAt
```

其中 **`sha256` 是校验基准**。缺了它，就等于「拿不到验收标准」。

**现在的处理**：解包成空字典 → 每个字段 `??` 兜底 → `expectedSHA` 为空串
⇒ SHA-256 校验必然不通过 ⇒ **该段被判定为损坏**，
文件被**移入 `corrupted/` 目录保留**（不是删除），并触发 `onSegmentCorrupted` 回调通知用户。

**这正是「数据一个字节都不丢」想要的保守行为** ——
宁可标脏隔离，也不静默入库当有效数据。

**验证步骤**：

1. 正常录一段，确认 iPhone 端能正常收到并入库（对照组）。
2. 构造 metadata 缺失的传输（最简单的方式：**在 iPhone 端打开飞行模式**，
   让传输在系统队列里排队期间 metadata 未能随文件送达；
   或用 Xcode 调试器在 `didReceive file:` 断点处把 `file.metadata` 置为 `nil` 再继续）。
3. 观察 iPhone 端行为。

**通过判据**：

- metadata 缺失时，该段**不会**被当作有效数据写进录音库索引；
- 该段被标记为**损坏**并有明确提示（不是静默丢弃）；
- **损坏段的文件仍在**（在 `corrupted/` 目录下，文件本身没被删）；
- App 不崩溃（这正是 `?? [:]` 解包的作用）。

**失败定位**：

| 现象 | 根因 |
|---|---|
| metadata 缺失时崩溃 | `file.metadata` 没解包（第 7 轮修的就是这个） |
| 缺 metadata 的段被静默当作有效数据入库 | 校验被跳过或 `expectedSHA` 为空时被当作「不校验」 |
| 损坏段的文件消失 | 没走 `corrupted/` 保留路径，直接删了 |

**对照代码**：`Sources/DayEchoApp/PhoneReceiveChannel.swift` 的
`let meta = file.metadata ?? [:]`（第 7 轮修复）、`corruptedDir` 保留逻辑。

## 4.5 重签装机参考路径（外部重签，无需重新编译工程）

> 本机只有 Command Line Tools、无 Xcode.app，**无法签名**。
> 但**不需要把整套工程搬到另一台 Xcode 机器重新编译** ——
> 可以直接对已产出的 `DayEcho-unsigned-macos15.ipa` 做**外部重签**。

### 准备证书

1. 在有完整 Xcode 的 Mac 上：Xcode → Settings → Accounts → 登录个人 Apple ID
2. Manage Certificates... → 生成一张 **Apple Development** 证书
   （免费个人 Apple ID 即可，**有效期 7 天**，真机实测完全够用）
3. 用 Xcode 新建一个**临时的空白 iOS App 工程**（Bundle ID 填 `com.dayecho.app`），
   连上 iPhone 点运行，或在 Signing & Capabilities 里让 Xcode 自动生成
   含你 iPhone UDID 的描述文件
4. 描述文件在 `~/Library/MobileDevice/Provisioning Profiles/` 里

### 嵌套重签（★ 顺序不能反 ★）

**必须先签内层 Watch App，再签外层 iOS App。**

```bash
# 1. 解包
mkdir -p /tmp/resign && cd /tmp/resign
unzip -q ~/Desktop/DayEcho-unsigned-macos15.ipa

# 2. 准备最简 entitlements
#    ★ 免费个人 Apple ID 默认不支持自定义 App Groups 等高级 entitlements ★
#    提示权限不足时用最简版：只保留下面三个键
cat > entitlements.plist <<'PLIST'
<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE plist PUBLIC "-//Apple//DTD PLIST 1.0//EN" "http://www.apple.com/DTDs/PropertyList-1.0.dtd">
<plist version="1.0">
<dict>
  <key>application-identifier</key>
  <string>XXXXXXXXXX.com.dayecho.app</string>
  <key>com.apple.developer.team-identifier</key>
  <string>XXXXXXXXXX</string>
  <key>get-task-allow</key>
  <true/>
</dict>
</plist>
PLIST

# 3. ★ 先签内层 Watch App ★
codesign --force --sign "Apple Development: 你的名字 (XXXX)"   --entitlements entitlements.plist   --generate-entitlement-der   Payload/DayEcho.app/Watch/DayEchoWatch.app

# 4. 再签外层 iOS App
codesign --force --sign "Apple Development: 你的名字 (XXXX)"   --entitlements entitlements.plist   --generate-entitlement-der   Payload/DayEcho.app

# 5. 重新打包
zip -qry DayEcho-signed.ipa Payload
```

3. 一键签名安装
