# DayEcho 复盘：为什么「编译通过」被当成了「功能验证」

> 复盘日期：2026-11-19
> 触发：连续两天在「装机」环节反复受阻（签名 / profile / Apple 账号），
> 而 App 本身能不能跑起来，从未被验证过。
> 结论先行：**过去四天的 CI 从未验证过「装上能不能启动」。这不是环境问题，是流程漏洞。**

---

## 0. 一句话

**我用了四天时间死磕「最难的路上真机」，却跳过了「最简单就能验证」的那条路。**

模拟器 runtime（iOS 26.3 / watchOS 26.2）在我折腾 Apple 账号之前就已经装在本机。
一条 `xcodebuild -destination 'platform=iOS Simulator'` 三分钟就能回答
「装上能不能启动」—— 不需要 profile、不需要证书、不需要 Apple 账号、不需要用户的 iPhone。

⇒ 这本身就是「没有装机门禁」的直接后果：**断言脚本和真实产物脱节了两天才被看到。**

## 2. 根因：把四件事当成了两件事

我在汇报里一直在用「编译成功」这个说法，实际上它只覆盖了第一件：

| # | 环节 | 我这四天验证了吗 | 怎么验证才算数 |
|---|---|---|---|
| 1 | **编译通过** | ✅ 天天验 | `xcodebuild` 返回 0 |
| 2 | **签名通过** | ⚠️ 部分 | `codesign -v` + entitlement 对齐 profile |
| 3 | **装得上** | ❌ **一次都没有** | 真机 `devicectl` / 模拟器 `simctl install` |
| 4 | **跑得起来不崩** | ❌ **一次都没有** | 拉起进程 + 等 10s + 查崩溃报告 |

**我把第 1 项的结果，反复当成第 3、4 项的证据。**

这正是记忆里早就写下的那条：**「★装上≠能启动」**。
它被记成了「注意点」，而不是「**门禁**」。

### 更深一层：环境把我带偏了

| 表面现象 | 当时的解释 | 真实原因 |
|---|---|---|
| 两天都在搞签名 | 「装机需要签名」 | 模拟器**根本不需要签名** |
| 一直等 profile | 「Watch 要 watchOS profile」 | 模拟器上 Watch **也能跑** |
| 死磕 Apple 账号 | 「没 profile 就没法装」 | 模拟器**完全绕开 Apple 账号** |

签名是最难、最不可控、最容易出挫败感的环节。
一旦开始死磕它，我就会不自觉地**把所有精力都吸进去**，
而**没有退一步问「有没有一条不需要签名的路能回答同样的问题」**。

⇒ 这是本次复盘最该记住的一条：
**当你在最难的路上连续受挫时，先退一步找最简可解释的验证路径，
而不是加大力度继续攻。**

## 3. 如果没有 Xcode，这些问题什么时候会被发现？

**答案：永远不会被发现。**

因为整条链路上「装上能不能启动」这一环从来就是断的，
而它恰好是**唯一一个不需要 Apple 账号的验证环节**。
只要缺了它，任何签名/账号问题都会成为「唯一可走的路」，
于是全部注意力都被吸到那条路上。

各问题本该的暴露时机：

| 问题 | 现在的暴露方式 | 本该在什么时候暴露 |
|---|---|---|
| Info.plist 键缺失 / 类型错 | 断言脚本（但两天没跑到） | 模拟器装上就报错 |
| App Group 不匹配 | 签名阶段（`codesign` 拒绝） | 模拟器装上就报错 |
| 断言脚本与产物脱节 | ★ 手动触发 CI 后 | 每次 push 必跑 |
| 启动即崩溃（EXC_BREAKPOINT） | 完全没暴露 | 拉起 + 等 10s |
| Widget 独立进程秒崩 | 历史上踩过一次，靠真机 | 模拟器拉起 Widget 进程 |
| `UIBackgroundModes` 冗余 | 我静态分析推出来的 | 运行时行为观察 |
| Live Activity 起不来 | 完全没验证过 | 模拟器触发 Live Activity |

**⇒ 改进不是「以后更小心」，而是「让 CI 每天自动回答这个问题」。**

`UIBackgroundModes` 期望值、`WKCompanionAppBundleIdentifier` 期望值
与真实产物对齐 —— 这两条断言从 11-17 起就是红的。

## 6. 给下一个接手的人（也包括我自己）

1. **不要用「编译通过」汇报装机结果。** 五件事分开说。

## 8. 门禁上线后第一个小时抓到的两个真实 Bug（2026-11-19 17:00）

★★ 这部分是本文最有价值的部分 ★★
**门禁上线不到一小时，就抓出了两个「编译通过 + 单测全绿 + 签名通过」都照样出错的 Bug。**
它们**从来没有被任何测试发现过**，因为从来没有人把 App 装到设备上。

### 8.1 Bug A：Bundle ID 与 Apple 实际签发的 App ID 不一致

**症状**（模拟器安装被系统直接拒绝）：

```
Invalid value of WKCompanionAppBundleIdentifier key in WatchKit 2.0
app's Info.plist: com.dayecho.app.H98V6YZ5QL (expected com.dayecho.app)
```

**根因链**：

1. `legal/gen_xcodeproj.rb` 里写的是 `BUNDLE_ID = 'com.dayecho.app'`（**不带 Team ID**）
2. 而 Apple 实际签发的 Team Provisioning Profile 里是
   `com.dayecho.app.H98V6YZ5QL`（**带 Team ID**）
3. 当时为了绕过签名失败，我**手工改了 `project.pbxproj`**，
   **但生成器 `gen_xcodeproj.rb` 没改**
   → CI 每次 `ruby legal/gen_xcodeproj.rb` 重新生成工程，**都退回不带 Team ID 的错值**
   → **CI 与本地产物根本不是同一个东西**
4. `WKCompanionAppBundleIdentifier` 也被我一并手工改成带 Team ID 的值
   → 与 CI 里宿主 App 的 Bundle ID 不匹配 → **系统拒绝安装**
5. 我还把 **App Group**（`group.` 前缀、带 Team ID）和
   **Bundle ID**（不带 `group.` 前缀）**搞混了** —— 这是同一个错误的两次体现

**为什么真机也会挂**：profile 里的 App ID 与 Bundle ID 不匹配，
真机安装同样会被拒。**这不只是模拟器的问题。**

**修复**（`e40dfdc`）：所有 Bundle ID 一律从 `TEAM_ID` 派生，杜绝手改后遗漏：

```ruby
TEAM_ID = ENV['DAYECHO_TEAM_ID'] || 'H98V6YZ5QL'
BUNDLE_ID = "com.dayecho.app.#{TEAM_ID}"
```

**教训**：
> ★ 手工改生成产物来绕过问题，等于给自己埋雷。生成器才是真源。
> ★ 一旦发现「本机能过、CI 不能过」，第一反应应该是查**生成器**，而不是查 CI。

### 8.2 Bug B：模拟器构建根本没挂 App Group entitlements

**症状**：CI 构建出的产物 `CODE_SIGN_ENTITLEMENTS` 为空。

**根因**：`gen_xcodeproj.rb` 里 `USE_APP_GROUP` 默认**关闭**，
理由写的是「免费 Personal Team 带 app-group 会签名失败」。
但本项目现在用的是**付费 Team**，Apple 签发的 profile 里本来就含
`group.com.dayecho.app.H98V6YZ5QL` ⇒ entitlements 与 profile 不一致。

**更隐蔽的后果**：
> 模拟器构建不挂 entitlements ⇒ **CI 验的 App Group 共享容器那条路，
> 跟真机上的完全不是同一件事** ⇒ 这条路在 CI 里等于从没被验过。

**修复**（`3e05a3a`）：默认改为开启，保留 `DAYECHO_APP_GROUP=0` 显式关闭。

### 8.3 门禁脚本自己也踩了坑

`shutil.glob` 在 Python 3.15 已被移除 → 收集崩溃报告时抛
`AttributeError: module 'shutil' has no attribute 'glob'` → 门禁 exit 1。

★ **这个 Bug 恰好证明门禁在起作用**：它不是「装不上就红」，
而是**每一步都有明确的成功断言**，任何一步不满足就红。

### 8.4 门禁全绿的样子（run 44572358224 实测）

```
✓ 模拟器已启动: iPhone 16e
✓ 安装成功: com.dayecho.app.H98V6YZ5QL
✓ LaunchServices 已登记 com.dayecho.app.H98V6YZ5QL
✓ 启动成功，PID=8319
✓ 进程存活（12s 后仍在运行）
```

★★★ **这是 DayEcho 四天以来第一次拿到「装上能启动」的硬证据。** ★★★

## 9. 元教训：门禁的价值不在「第一次就绿」

门禁第一次跑的时候是**红的**，而且红在三处不同的层：

| 层次 | 红的原因 | 性质 |
|---|---|---|
| `Assert Info.plist required keys` | 我改了 plist 没同步断言脚本 | 断言脱节 |
| `Assert simulator install and launch` | **Bundle ID 与 profile 不匹配** | ★ 真实产品 Bug ★ |
| 同一个门禁的收尾 | `shutil.glob` 在 3.15 移除 | 脚本自身 Bug |

★ 如果没有这道门禁，以上三个问题**会一直留到真机装机那一刻**，
而真机装机那一刻还要再叠加签名、profile、Apple 账号三道坎。

**⇒ 门禁的价值不是「让 CI 变绿」，是「让 Bug 在便宜的地方暴露」。**

## 10. Watch App 秒崩：依附式链路从没被验过的代价

### 10.1 症状

Watch App 在 watchOS 模拟器上**装得上、登记得了、launch 也返回 PID**，
但 12 秒后进程就没了 ⇒ 门禁报「进程立刻退出了」。

★ 单看「装得上 + launch 有 PID」会以为没问题 ——
**PID 返回 ≠ 进程活着**，这是第五阶段验收存在的理由。

### 10.2 真实根因（崩溃报告原文）

`~/Library/Logs/DiagnosticReports/DayEchoWatch-2026-11-20-023536.ips`：

```
exception:   EXC_CRASH / SIGABRT
namespace:   WATCHKIT
reasons:     Condition failed:"NO".
             -[WKApplication scheduleBackgroundRefreshWithPreferredDate:userInfo:scheduledCompletion:]
             requires that your WKApplicationDelegate (null) implement handleBackgroundTasks:
```

拆开看：

1. `WKApplicationDelegate (null)` ⇒ **delegate 是 nil**
2. `scheduleBackgroundRefresh` 在 delegate 为 nil 时**不是抛异常，是系统
   precondition 失败 → 直接 SIGABRT 杀进程** ⇒ `catch` 根本拦不住
3. 为什么 delegate 是 nil？SwiftUI 的 `@WKApplicationDelegateAdaptor`
   是在 **App 主体初始化之后**才把 delegate 注入 `WKApplication` 的，
   而我们的 `App.init()` 里就直接调了 `coordinator.scheduleBackgroundRefresh()`
   ⇒ **必然踩到 delegate == nil**

★ **为什么四天没发现**：因为 Watch App **从来没在模拟器上真跑过**。
编译通过 ≠ 运行通过；依附式链路的错误只在**运行**时暴露。

★ **注意我们自己的协议实现是对的**：
ObjC 的 `handleBackgroundTasks:` 对应 Swift 的 `handle(_:)`，
SDK 头文件 `WKApplication.h` L84 已确认签名一致 ——
所以不是「方法名写错了」，而是「调用时机早于 delegate 就绪」。

### 10.3 修复

```swift
// 1) 协调器：delegate 未就绪就挂起，绝不直接调 API
guard WKApplication.shared().delegate != nil else {
    pendingBackgroundRefresh = true
    return false
}

// 2) delegate 就绪后补调度
func applicationDidBecomeActive() {
    Task { @MainActor in
        WatchSessionCoordinator.shared.flushPendingBackgroundRefresh()
    }
}
```

### 10.4 修复前后对照（实测）

| | 崩溃报告 | 进程 |
|---|---|---|
| 修复前 | `DayEchoWatch-2026-11-20-023536.ips`（SIGABRT） | 秒退 |
| 修复后 | **无崩溃报告** | 持续存活 |

## 11. 门禁自己也骗人：三个「假绿/假红」

门禁写完后第一版在 Watch 上判「进程死了」，但进程其实活得好好的。
查下来是**门禁自己的三个缺陷**：

### 11.1 崩溃检查形同虚设（假绿）

```python
if bundle_id.split(".")[-1] in f:
```

`com.dayecho.app.H98V6YZ5QL` 取最后一段是 **Team ID `H98V6YZ5QL`**，
而崩溃文件名用的是**可执行名**（`DayEchoWatch-2026-11-20-023536.ips`）
⇒ **永远匹配不到任何崩溃文件**。

★ 所以之前那句「✓ 无崩溃报告」是**无条件打印的** ——
哪怕真的崩了，门禁也看不见。

**修复**：从 bundle id 反推可执行名，并做正反验证：

```
匹配 DayEcho-2026.ips     : True
匹配 DayEchoWatch-2026.ips: True
不匹配 Safari-2026.ips     : False
```

### 11.2 进程存活检查用错了键（假红）

`launchctl list` 里 iOS 与 watch 的条目形态**不一样**：

```
iOS  : DayEcho
watch: UIKitApplication:com.dayecho.app.H98V6YZ5QL.watchkitapp[7d23][rb-legacy]
```

按可执行名 `DayEchoWatch` 去 grep ⇒ 永远匹配不到 ⇒
**把「活得好好的」判成「秒崩」**。

**修复**：两种形态都试 + bundle id 兜底 + 忽略大小写。

### 11.3 并发 simctl 互相锁死（假挂死）

本机曾同时有 **5 个 `simctl install` 进程**并发，全部无输出卡死。
这不是环境问题，是**门禁缺设备级互斥锁**。

**修复**：`fcntl` 设备级锁 + install 阶段失败诊断
（此前 install 失败只报 `rc=124`，无任何线索）。

### 11.4 一条环境结论

本机 Simulator **窗口数为 0**、`screencapture` 报
`could not create image from display` ⇒ 本地 Simulator 起不来显示上下文。

⇒ **本地只适合「构建 + 静态检查」，install/launch 的判据只能靠 CI runner。**
但只要遵守「单设备 Booted + `open -a Simulator` 后等 25s」，
本地 install 是能成功的（实测 `INSTALL_RC=0`），
可以当**快速预筛**用。

## 12. 两条要带走的元教训

### 12.1 「有 PID」不等于「活着」

Watch App 那次 `simctl launch` 明明返回了 PID，
但进程 12 秒后就没了。⇒ 验收必须区分：

```
编译通过 → 签名通过 → 装上 → 启动返回 PID → 持续存活 → 无崩溃 → 功能验收
```

★ 每一层都要**独立断言**，不能上一层过了就假定下一层也过。

### 12.2 门禁自己也可能是 Bug 来源

这一轮门禁抓出了 2 个真 Bug，但也自己制造了 3 个假信号
（崩溃检查形同虚设、进程检查误判、并发互锁）。

⇒ **门禁不是「写了就信」，它自己也要被证伪**。
每次门禁判红，先问一句：「**是产品坏了，还是门禁自己坏了？**」

★ 这次正是靠「进程明明在 `launchctl list` 里，门禁却说它死了」
这句话定位到的。

## 13. 门禁第二次自我审查：三个"我自己造的假信号"

第 11 章修完门禁后，**我以为**它已经可信了。
把它推上 CI 一跑 —— 红。而且这次的锅**全在门禁自己身上**。

### 13.1 崩溃名匹配：我连踩三次

第一次（11.1 已修）用 `bundle_id.split(".")[-1]` ⇒ 拿到 Team ID。
修完以为对了，**造真实文件名一测**才发现：

**坑 A：无条件塞 "DayEcho" 进候选**

```python
candidates.add("DayEcho")   # ← 无条件
```

结果 `com.apple.mobilesafari` 也能"抓到"DayEcho 的崩溃
⇒ **跨 target 误判**：检查 Safari 时以为自己崩了。

**坑 B：用泛包含匹配**

```python
if c.lower() in low:   # ← 包含
```

`"dayecho"` 是 `"dayechowidget"` 的**子串**
⇒ **主 App 会误抓 Widget 的崩溃**。

**坑 C：Team ID 不在末尾**

```
com.dayecho.app.H98V6YZ5QL              → Team ID 在末段
com.dayecho.app.H98V6YZ5QL.watchkitapp   → Team ID 在倒数第二段
```

我按"末段是大写 10 位就剥"的规则，后一种根本剥不掉
⇒ 候选退化成空 ⇒ 什么都不匹配。

**最终解法**：把崩溃文件名解析成**词干**（第一个 `-` 之前的部分），
与该 bundle id 推导出的可执行名做**精确比对**，并按 token 语义
组合后缀（`watchkitapp`→Watch，`widget`→Widget）。

实测矩阵（造 5 个真实文件名验证）：

| bundle id | 期望匹配 | 实得 |
|---|---|---|
| `...H98V6YZ5QL` | DayEcho | ✅ DayEcho |
| `...H98V6YZ5QL.widget` | DayEchoWidget | ✅ DayEchoWidget |
| `...H98V6YZ5QL.watchkitapp` | DayEchoWatch | ✅ DayEchoWatch |
| `...watchkitapp.widget` | DayEchoWatchWidget | ✅ DayEchoWatchWidget |
| `...watchkitapp.watchwidget` | DayEchoWatchWidget | ✅ DayEchoWatchWidget |
| `com.apple.mobilesafari` | （不匹配） | ✅ 空 |

★ **教训：匹配逻辑必须造真实数据跑，不能靠读代码确认。**
★ 我读代码时"看起来是对的"，三次都错了。

### 13.2 launch 会间歇性挂死 ⇒ 门禁必须能重试

同一份代码，两个 run：

| run | launch 耗时 | 结果 |
|---|---|---|
| 44584285050 | **4 秒** | ✅ |
| 44593603881 | **300 秒超时挂死** | ❌ |

根因是 CI runner 负载高时 `simctl launch` 等 launchd/SpringBoard
响应不及时 —— **不是产品问题**。

★ 但门禁**分不清**这两者。所以加了 **3 次独立计时的重试**：
只有全部失败才判红。判红时也会打印"第 N 次启动超时（simctl 在
runner 上挂死）"，让人一眼看出是环境还是产品。

### 13.3 级联假象：误导性根因比没根因更糟

run 44593603881 真正失败的是 simulator launch 挂死。
但紧随其后的诊断步骤报的是：

```
❌ 未找到 Release-iphoneos/DayEcho.app
```

—— 因为 device build **根本没跑**（被前置失败跳过）。

★ 这类"下游因上游失败而报出的错"会**把排查方向带偏**：
看日志的人会去查"为什么产物没生成"，而真正的原因是三步之前的 launch 挂死。

修法：
- 产物不存在 ⇒ 改 `::notice::` + `exit 0`，只补充诊断信息，不制造第二个失败信号
- `Pre-Package` 里的 `::error::` annotation 也改掉
  （★ annotation 本身就会把 job 判红，**即使 exit 0** —— 这是个容易漏的坑）

### 13.4 一条通用的门禁设计原则

> **门禁的每个失败信号，都必须是"这一层自己的问题"。**
>
> 如果某一步失败是因为上游没跑，
> 那它就不该再报一个错 —— 它应该**只输出诊断信息**，
> 把"哪一步先失败"这件事留给第一个失败信号去表达。

★ 这条原则同时解释了 13.1（匹配逻辑必须精确）、
13.2（环境问题要能区分）和 13.3（下游别重复报错）。

## 14. App Group 共享容器：装得上、起得来，仍然可能**共享不了**

CI run `44603533835` 第一次全绿（iOS 门禁 + Watch 门禁 + device 构建 +
archive + 打包，全部 ✓）。我以为这条线收口了。

然后我补了一道门禁去验「共享容器到底通不通」——
**当场抓到第三个静默失效**。

### 14.1 抓到的事实

```
✓ [app]    App Group entitlement 正确: group.com.dayecho.app.H98V6YZ5QL
✗ [widget] 签名里没有 App Group entitlement
            entitlements keys = ['application-identifier']
```

★ **Widget target 压根没配 `CODE_SIGN_ENTITLEMENTS`。**

`project.pbxproj` 里只有 4 处 `CODE_SIGN_ENTITLEMENTS`，
分别指向 `legal/DayEchoApp.entitlements`（主 App）和
`legal/DayEchoWatchApp.entitlements`（Watch App）
—— 两个 Widget target 一个都没有。

后果：**Widget 有独立沙盒，没有 App Group ⇒ 主 App 写进共享目录的
数据，Widget 一个字都读不到。**

★ 而这一切**没有任何一行报错**：Widget 装得上、起得来、
界面正常，只是显示的内容永远不对。

### 14.2 为什么之前没人发现

因为「共享」这件事**无法靠编译发现**，也无法靠装上发现，
更无法靠启动发现 —— 它只能在**真的读一次共享目录**时暴露。

而我们从没写过"从 Widget 进程读共享目录"的测试。

⇒ 这就是为什么必须有独立的 App Group 门禁：
**共享是第四种失败模式**，前三种（装不上/起不来/编译不过）都已被覆盖。

### 14.3 门禁断言三件事（缺一不可）

| # | 断言 | 挡住什么 |
|---|---|---|
| A | 每个 target 的**签名信息**里都有正确的 app-group entitlement | 源码写了但没生效 |
| B | 各 target 的 group id **完全一致** | 主 App 和 Widget 用不同 id，互相看不见 |
| C | 模拟器上**真的存在**这个 group 容器目录 | entitlement 没被系统接受 |

★ A 读的是**签名信息**，不是源码 —— 这是刻意的：
源码里有 `com.apple.security.application-groups` 不代表它进了产物。

★ C 查的是 CoreSimulator 的 container manager 建的目录
（带 `.com.apple.mobile_container_manager.metadata.plist`），
不是我们自己 `mkdir` 出来的 —— 所以它证明的是**系统接受了**。

### 14.4 读 entitlement 踩的三个坑

写这个门禁时自己踩了三个坑，都表现为"明明有却读不到"：

**坑 1：codesign 返回空 dict 就提前 return**

模拟器产物常把 entitlements 放进 `__TEXT __entitlements` 段，
而 `codesign -d --entitlements -` 读出来是**空 dict**。
一开始我在那里 `return` ⇒ 永远走不到 otool 分支 ⇒ 读不到。

**坑 2：把 `otool -s` 整段输出当 hex 串 strip**

`otool -s` 每行是「地址\t字节 字节 ...」，
把整段输出 `re.sub("[^0-9a-f]","")` 会把**地址行也混进去**，
解出来的字节流是乱的。
⇒ 必须只取制表符之后的部分，逐行收集字节。

**坑 3：可执行文件名 ≠ 目录名**

`bundle_path = ".../DayEchoWatch.app"` ⇒ 目录名是 `DayEchoWatch.app`，
但可执行文件叫 `DayEchoWatch`。
直接拼路径得到 `.../DayEchoWatch.app/DayEchoWatch.app` ⇒ 不存在。
⇒ 优先读 `Info.plist` 的 `CFBundleExecutable`。

★ 这三个坑的共同点：**都是"读代码看起来对、真跑不对"**。
⇒ 和第 13.1 节同一个教训：匹配/解析逻辑必须造真实数据跑。

### 14.5 顺带修的 Watch 侧同一个洞

CI 的 watchOS 模拟器构建用的是 `CODE_SIGNING_ALLOWED=NO`
⇒ Watch App **也没有** App Group entitlement
⇒ Watch 与 iPhone 在模拟器上根本不是"两个进程看同一份数据"。

已一并改为 ad-hoc 签名（与 iOS 侧对齐）。

★ 附带价值：CI 里 watch 模拟器构建也改成 ad-hoc 后，
两个 Watch target（Watch App + Watch Widget）现在都带 entitlement，
而此前它们是**两个都没带**。
