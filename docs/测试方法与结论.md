## 二、测试方法

### 2.1 为什么用「自研 runner」而不是 pytest / XCTest

本项目是 Swift Package，`DayEchoKit` 是纯逻辑层（不依赖 UIKit/WatchKit），
所以可以在 Mac 上直接跑。选型对比：

| 方案 | 问题 |
|---|---|
| XCTest | 需要 Xcode + iOS Simulator，本机没有 Xcode；纯 Swift 逻辑测试被迫绑到模拟器启动，慢且脆 |
| swift-testing | 需要 Swift 6 工具链，且 `Package.swift` 里 `DayEchoKit` 用的是 `.swiftLanguageMode(.v5)`，混用模式会带来额外编译噪音 |
| **自研 runner（采用）** | 零依赖、单进程、输出可读、退出码明确（0=全绿，1=有失败）、CI 里一行 `swift run DayEchoTestRunner` 就能用 |

自研 runner 在 `Sources/DayEchoTestRunner/`：
- `main.swift` —— 入口，按组依次调用测试函数
- `Tests/Assert.swift` —— 断言层（`checkEqual` / `checkNotNil` / `Suite.case_`）
- `Tests/DayEchoKitTests.swift` —— 存储 / 队列 / 校验 / 保留策略
- `Tests/DeviceReadinessTests.swift` —— A–F 六组上机前验证套件
- `Tests/BoundaryTests.swift` —— G1–G4 四组核心 Bug 边界套件

### 2.2 怎么跑

```bash
cd /Users/maike/Desktop/DayEcho

# 编译
swift build --product DayEchoTestRunner

# 跑（注意：不要用 swift run，stdout 会被吞，要跑二进制）
./.build/debug/DayEchoTestRunner > /tmp/testout.txt 2>&1; echo "exit=$?"

# 看结果
tail -3 /tmp/testout.txt
grep -c '✓' /tmp/testout.txt
```

实测输出：

```

```

`grep -c '✓'` 实测 = `66`，与汇总数字一致（交叉验证，不是只看汇总行）。

| 层 | 手段 | 覆盖 | 本机可跑 |

### 3.2 4 个 Bug 的修复 → 单测映射

#### Bug #1 时间戳计算错误

**旧算法**：`startedAt + (elapsed - segmentSeconds)`

**为什么错**：每一段的 `elapsed` 都 ≈ `segmentSeconds`，所以每一段算出的起点
都 ≈ `startedAt` ⇒ **所有段的时间戳挤在同一处**，iPhone 上时间线彻底失真。

**新算法**：`SegmentClock` 维护 `currentSegmentStart`，封段时取**重新观测的
`Date()`** 作为下一段起点，起点严格递增、不重叠、不漂移。

**单测**：
- `G1-1` 连续切段的时间戳连续且不重叠
- `G1-2` 误差不逐段累积（反推算法会平方级放大）
- `G1-3` `stop()` 尾段与前一段时间连续
- `A1` / `A2` 段起点独立记录、每段时间戳各不相同（回归测试，直接锁住旧 bug）

**方法要点**：为了让断言可计算，给 `SegmentWindow` 加了 `sealedAt`（封存时刻），
测试用 `sealedAt` **链式推导**下一段的 `now`，而不是手填常量——
手填常量容易写成「两段传同一个时刻」这种自欺欺人的断言。

#### Bug #2 落盘初始状态错误

**旧**：落盘默认 `.recorded` ⇒ 保留策略可能把还没传出去的录音删掉。

**新**：落盘默认 `.pending`；`applyRetention` **严格只扫 `.verified`**。
`.pending` / `.inFlight` / `.transferred`（待 ACK） / `.corrupted` 一律保留。

**单测**：
- `G2-1` 落盘默认态是 `.pending`（不是 `.verified`）
- `G2-2` 保留策略不删未传输 / 传输中 / 待 ACK / 损坏的段（**四种状态逐一验证**）
- `G2-3` 只有 `.verified` 才被保留策略清理
- `B1`–`B5` 旧套件覆盖同一条不变量的其他侧面

**方法要点**：新增了 `SegmentTransport.deliversAcknowledgement` 属性，
把「投递完成」和「已收到手机端 ACK」区分开。
不区分的话，`TransferCoordinator` 会把「文件传完但校验没过」的段误标成已验证 ——
这是 4 个 bug 里最隐蔽的一个，因为它只在「传输成功但校验失败」时触发。

#### Bug #3 `.inFlight` 死锁

**旧**：进程被杀后残留 `.inFlight`，重启后该段**永远不会被重新投递** ⇒ 录音静默丢失。
（这正是竞品 Auday 式卡死的机制。）

**新**：
- 冷启动恢复入口 `PendingTransferQueue.decode` 自动把残留 `.inFlight` 打回 `.pending`
- 运行期 `nextBatch` **绝不捞取**正在传输中的条目（防重复投递）

**单测**：
- `G3-1` 冷启动时残留 `inFlight` 全部重置为 `pending`
- `G3-2` 运行期 `nextBatch` 不捞取正在传输中的 `inFlight`
- `G3-3` 队列持久化往返后残留 `inFlight` 自动重置
- `G3-4` 重置**不影响**等待 ACK 的段（`.transferred` 不被误伤）

**方法要点**：G3-3 特别重要 —— 只测「内存里重置」不够，
必须测**序列化→反序列化**之后仍然重置，因为真实冷启动走的就是磁盘往返。

#### Bug #4 `stop()` 尾段丢失 + 双封存

**旧**：`stop()` 只停录音器，**最后一段从来没被封存过** ⇒ 每次停止录音，尾段（可能几十秒）直接丢失。

**新**：
- `stop()` 走 `RecordingSealer.endSessionAndSealTail()` 补封尾段
- 定时器切段和手动 stop() 都先问 sealer「轮得到你封吗」
- 撞车时**只有一方真正执行封存** ⇒ 既不双封存，也不丢尾段

**单测**：
- `G4-1` `stop()` 必须执行一次尾段封存
- `G4-2` 定时器先封存后 `stop()` 不双封存
- `G4-3` `stop()` 先封存后定时器不双封存
- `G4-4` 重复 `stop()` 尾段只封一次
- `G4-5` 定时器切段后可开始下一段并再次封存
- `G4-6` 定时器封段后 `stop()` 仍封存当前段（尾段不丢）

**方法要点**：G4-2 和 G4-3 是**一对** —— 必须双向都测。
只测「定时器先」会漏掉「stop 先」路径下的双封存。
G4-6 单独存在是因为「定时器刚切过段，用户马上停止」是最容易丢尾段的时序。

### 3.3 API 校正（4 处硬错误）

这 4 处曾是**编译期或运行时必炸**的错误，全部对照 Apple 官方文档修正：

| # | 错误用法 | 正确用法 | 后果 |
|---|---|---|---|
| 1 | `WCSessionTransfer` | `WCSessionFileTransfer` | 类型不存在，编译必炸 |
| 2 | `session(_:didReceive file:error:)` | `session(_:didReceive file:)` | 回调不触发，文件收不到 |
| 3 | `scheduleBackgroundRefresh(withIdentifier:)` 闭包 | `scheduleBackgroundRefresh(withPreferredDate:userInfo:)` + `WKApplicationDelegate` | 后台刷新永不触发 |
| 4 | `setTaskCompleted(success:)` | `setTaskCompletedWithSnapshot(false)` | 编译失败 |

**为什么这些没被单测抓到**：它们都在 `DayEchoWatchApp` / `DayEchoApp` 层，
依赖 `WatchKit` / `WatchConnectivity`，**不在 Mac SDK 里**，L1 单测层覆盖不到。
这正是 L2 语法检查和 L3 CI 编译存在的理由 —— 但要清楚：
**语法检查也抓不到这些**（它们语法是对的，是类型不存在）。
只有 L3 真编译才能抓到。所以 CI 必须过。

### 3.4 过程中被单测抓到的自身错误（诚实记录）

写测试的过程本身也暴露了 5 个我写错的地方，都已修正：

| # | 我犯的错 | 怎么被抓到的 | 修正 |
|---|---|---|---|
| 1 | `G1-2` 断言「误差不累积」时把「不累积」误算成「无误差」 | 断言失败，实测差值 1.8 ≠ 期望 2.0 | 改为验证差值**线性**增长（反推算法会平方级放大） |
| 2 | `G1-2` 基准算错：用了「最后一段起点」当基准 | 差值 -58.2，明显异常 | 改用「末段起点 - 会话起点」 |
| 3 | `G1-2` 期望切段次数多算 1 次 | 1.8 vs 2.0 | 末段起点之前只发生了 9 次切段，不是 10 次 |
| 4 | `A1`/`A2` 测试里 `now` 传了重复时刻 | 段起点相同 | 改用 `sealedAt` 链式推导 |
| 5 | `BridgeTransport` 没实现新协议属性 → **构建失败** | `swift build` 报 `error:`，跑的是旧二进制 | 补上 `deliversAcknowledgement` |

**第 5 条值得单独强调**：我一度以为「66/0 全绿」，实际是**构建失败后跑着旧二进制**。
判据是 `swift build` 的 `error:` 输出 —— 不能只看测试输出。
现在固定用 `swift build --product DayEchoTestRunner 2>&1 | grep 'error:'` 先确认构建成功，再跑二进制。

### 4.2 失败根因（日志已确认，不再是猜测）

日志通过 API 直接取（run 未结束时 `gh run view --log-failed` 不给日志）：

```bash
gh api repos/lengocdai102-hub/DayEcho/actions/jobs/131340798598/logs > /tmp/joblog.txt
grep -n 'error:' /tmp/joblog.txt
```

拿到**两个独立根因**：

#### 根因一：Kit 源文件漏加进 Xcode target

```
error: cannot find type 'TransferCoordinator' in scope        (WatchApp.swift:49)
error: cannot find 'RecordingSealer' in scope                   (WatchApp.swift:100)
error: cannot find type 'SegmentTransferResult' in scope        (WatchTransferChannel.swift:28)
error: cannot find type 'SegmentTransport' in scope             (WatchTransferChannel.swift:22)
```

**为什么本机绿、CI 红**（这是本次最值得记住的一点）：

| 构建系统 | 源文件来源 | 结果 |
|---|---|---|
| SwiftPM（`swift build`、CI 的 `swift run DayEchoTestRunner`） | **自己 glob** `Sources/DayEchoKit/` | 全绿 |
| Xcode 工程（`legal/gen_xcodeproj.rb` 生成） | **手写枚举** `kit_files = %w[...]` | 缺 4 个新文件 |

我新增了 `RecordingSealer.swift` / `SegmentClock.swift` / `TransferCoordinator.swift` /
`Acknowledgement.swift` 四个文件，只改了 SwiftPM 那边（隐式生效），
**忘了改 Xcode 工程那边的枚举**。

⇒ 两套构建系统的源文件列表不一致，SwiftPM 全绿完全掩盖了这个问题，
只有真机编译阶段才炸。

**修**：`kit_files` 改用 `Dir.glob` 自动收集。

```ruby
kit_files = Dir.glob(File.join(ROOT, 'Sources/DayEchoKit/**/*.swift'))
             .map { |p| p.sub("#{ROOT}/", '') }
             .sort
raise '★ DayEchoKit 源文件为空 —— glob 失败？' if kit_files.empty?
```

**本地实测验证**（不需要等 CI）：

```bash
ruby legal/gen_xcodeproj.rb
# 修复前： kit: src=4   wkit: src=4
# 修复后： kit: src=7   wkit: src=7
```

`kit_files` 被 iOS 和 watchOS 两个 Kit target 共用，所以改一处修两处。

#### 根因二：watchOS 上 override 了不可用的 delegate 方法

```
error: cannot override 'sessionDidBecomeInactive' which has been marked unavailable
error: cannot override 'sessionDidDeactivate' which has been marked unavailable
```

`WCSessionDelegate` 的这两个方法在 **watchOS SDK 里标为 `@available(iOS, unavailable)`**
—— 它们是 iOS 专属的。

**为什么 watchOS 不需要它们**：
它们处理的是 **iPhone → Watch** 方向的会话失活（iPhone 锁屏导致手表侧会话停用）。
而 DayEcho 的传输方向是 **Watch → iPhone**（手表录音传到手机），
手表这一侧不会因为 iPhone 锁屏而失活 ⇒ 这两个回调在 watchOS 上没有语义。

**修**：删除这两个方法，保留 watchOS 真正需要的
`session(_:activationDidCompleteWith:error:)`。

**修完后的实测**：`swiftc -parse` 语法检查全过（但注意 —— 语法检查抓不到
「类型不存在」和「方法不可 override」这两类错误，只有真编译能抓，
所以 CI 这一步不能省）。

### 4.3 这次失败暴露的方法论问题（已写进防回退）

**教训 1：两套构建系统的源文件列表必须自动同步。**
手写清单 = 迟早会漏。改成 glob 是根治。

**教训 2：本地绿 ≠ 能编译。**
本机没有 iOS/watchOS SDK，只能验语法。语法正确 ≠ 类型存在 ≠ API 可用。
L1（单测）/ L2（语法）/ L3（真编译）三层缺一不可。

**教训 3：CI 日志要会用 API 直接拉。**
`gh run view --log-failed` 在 run 未结束时直接拒绝返回，
用 `gh api .../actions/jobs/<job_id>/logs` 可以拿到已结束 job 的完整日志，
不用干等整个 run。

### 4.4 runner 排队的情况

workflow 用的是 `macos-15` / `macos-26`（Intel）。
之前实测这两个标签**秒级可用**，本次排队 5 分钟后即开跑 —— 属正常波动。
（`macos-13` 已被 GitHub 下线；arm64 标签在免费账户上要排 90+ 分钟，已刻意避开。）

### CI 失败时的标准排查动作（本次已验证可用）

```bash
# 1) 看 run 状态
gh run list --limit 3

# 2) 看是哪个 job、哪个步骤挂了
gh run view <run_id>

# 3) ★ 关键 ★ run 未结束时 gh view 不给日志，用 API 直接拉已结束 job 的
gh api repos/lengocdai102-hub/DayEcho/actions/jobs/<job_id>/logs > /tmp/joblog.txt

# 4) 抓真正的编译错误（不要被 ::error:: 之类的 echo 行带偏）
grep -n 'error:' /tmp/joblog.txt | grep -v '::error::'
```

第 3 步是本次新学到的 —— 否则只能干等整个 run 结束。
