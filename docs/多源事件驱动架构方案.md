# DayEcho 多源事件驱动架构方案（送 Gemini 论证稿）

**日期**：2026-11-13　**状态**：技术可行性已逐条取证，附官方证据
**结论摘要**：方向**成立且更优**，但落地路径与您设想的不同 —— iOS 上「用户授权读别人的邮件/短信」**没有公开 API**，
能落地的官方通道有 **4 条**，其中 **2 条是「用户主动转发」而非「App 自行读取」**。
详见第 2 节逐通道取证表。

---

## 0. 本文档的目的与取证方法

您的主张：**不做全天录音，改为「用户授权读取邮件通知 / 短信通知 / 电话录音 / 真人对话」的事件驱动混合模式**，
理由是：这些事件不是整天发生 ⇒ 不耗电；覆盖面更广（生活方方面面）。

本文档**不否定这个方向** —— 我们认为它在产品层面比全天录音更优。
但我们必须先把它落到**具体的 iOS 官方 API** 上，否则方案会建在错误前提上。

**取证方法**（全部实测，非记忆）：
- Apple 开发者文档 JSON 端点：`https://developer.apple.com/tutorials/data/documentation/<path>.json`
  —— **HTTP 200 = 该 API 真实存在；404 = 从未存在**（比 scrape JS 页快一个数量级）
- App Store Review Guidelines 全文抓取并逐条切片
- 日期锚点：2026-11-13

> ⚠️ **口径声明**：本文档的「不存在」= **在 Apple 公开文档索引中查不到**，
> 不等于「Apple 从未做过」。私有 API（如 `SPMessagesAccount`）在越狱/企业场景存在，
> 但 **App Store 审核指南 2.5.1 明令「Apps may only use public APIs」** ⇒ 私有 API 不可用于上架产品。

## 1. 关键裁决：iOS 上「用户授权」能授权到什么程度

这是整个方案的分水岭。我们把它拆成三个层级：

| 层级 | 含义 | 存在性 | 证据 |
|---|---|---|---|
| **L1 系统级授权** | App 拿到一个系统弹窗，点「允许」后即可读该类数据 | **仅限麦克风、相册、通讯录等固定清单** | `MFMessageComposeViewController` 的 abstract 明确写 "lets the user compose and send SMS" —— **只有发，没有读** |
| **L2 用户主动投递** | 用户**自己**把内容送进我们的 App（转发、共享、快捷指令） | ✅ **可用且合规** | `AppIntents` / `CoreSpotlight` / 通知内容扩展（需实测） |
| **L3 静默后台读取** | App 在后台自行抓取别家 App 的邮件/短信/通话 | ❌ **无公开 API** | 见第 2 节逐条取证 |

### ★ 决定性条款（逐字引用，App Store Review Guidelines）

> **2.5.1** Apps may only use **public APIs** and must run on the currently shipping OS.
> Learn more about public APIs. … Apps should use APIs and frameworks for their **intended purposes**…

> **5.1.1 (iii) Data Minimization**: Apps should only request access to data relevant to the core functionality
> of the app… Where possible, use the out-of-process picker or a **share sheet** rather than requesting full access…

> **5.1.1 (iv) Access**: Apps must respect the user's permission settings and **not attempt to manipulate, trick,
> or force people to consent** to unnecessary data access.

> **5.1.2 (i)** Unless otherwise permitted by law, you may not use, transmit, or share someone's personal data
> **without first obtaining their permission**. … You must clearly disclose where personal data will be shared
> with third parties, **including with third-party AI**, and obtain explicit permission before doing so.

> **2.5.14** Apps must request explicit user consent and provide a **clear visual and/or audible indication
> when recording**, logging, or otherwise making a record of user activity.

**这五条合起来定义了「用户授权」在 iOS 上的合法形态：**
1. 只能用公开 API（⇒ 不能逆向、不能读别人 App 的私有数据库）
2. 必须是**最小必要**（⇒ 不能申请「全量短信访问」这种笼统权限）
3. 必须**可撤回**、不能诱导
4. 第三方数据需**明确披露**并单独取得同意（⇒ 电话另一端、邮件发件人的内容不能默认算「用户已授权」）
5. 录音必须**显式同意 + 持续可见指示**

## 2. 逐通道可行性取证表（每条都有实测证据）

### 2.1 邮件通知 —— ⚠️ 无「App 自行读取」的公开 API，但有 3 条合规替代路径

| 探测目标 | 结果 | 证据 |
|---|---|---|
| `serviceprovidermanager` / `serviceprovider/spmessages` / `serviceprovider/spaccount` / `servicemanagement/spmessagesaccount` | **全部 404** | Apple 文档 JSON 端点 + `.md` 端点双探测 |
| `mailkit` | **存在，但 `platforms = [macOS12.0]`** | 只有 `MEExtension`（macOS 邮件插件），**iOS 上不存在** |
| `messageui/mfmessagecomposeviewcontroller` | **存在（iOS4.0+）**，abstract = "lets the user **compose and send** SMS or MMS" | **只能发，不能读** |

**结论**：Apple Mail 的消息读取能力（Service Provider Manager，简称 SPM）**在 iOS 上没有公开的 App Store 可用通道**。

**但用户提的「邮件通知」有个更好的落点 —— 那正是 *通知*，而通知有官方扩展机制。**
见 2.4。

### 2.2 短信 —— ❌ 确认无公开读取 API

| 探测目标 | 结果 |
|---|---|
| `sms` / `messagedata` / `messagedata/mdm` | **全部 404** |
| `messageui/mfmessagecomposeviewcontroller` | 存在，但**只能发** |

**结论**：iOS **没有任何**第三方 App 可读取用户收件箱短信的公开 API。
`MFMessageComposeViewController` 是**发送**用，abstract 原文写明 "compose and **send**"。

### 2.3 电话通话录音 —— ⚠️ 通话「事件」可获知，通话「内容」不可获知

| 探测目标 | 结果 | 意义 |
|---|---|---|
| `callkit/cxcall` | ✅ iOS10.0+ | 通话对象存在 |
| `callkit/cxcallobserver` | ✅ iOS10.0+ | **可观察通话状态变化（响铃/接通/挂断）** |
| `callkit/cxprovider/reportnewincomingcall(with:update:completion:)` | ✅ iOS10.0+ | **可获知来电事件** |
| `avfaudio/avaudiosession` | ✅ iOS3.0+ | 音频会话配置 |

**关键区分**（这是您方案里必须分开写的两件事）：
- ✅ **「通话发生了」** —— `CXCallObserver` 能拿到**通话开始/结束/时长/对方号码**。
  这是「事件」，正是您要的。
- ❌ **「通话说了什么」** —— iOS **不允许**第三方 App 录到蜂窝通话双方音频。
  `CallKit` 管的是**你的 App 自己的 VoIP 通话**（`CXProvider` = 你做 VoIP 服务商），
  不是系统电话的旁路录音。系统电话录音只有两条路：
  1. iOS 18.1+ 的**通话录音**功能（系统内置，用户手动开，需双方同意，**App 拿不到数据**）
  2. 用户自己装第三方录音 App（走 App Store 审核，且状态栏会显示橙色录音指示）

### 2.4 通知内容扩展 —— ★ 最可能是您要的「授权读取邮件/短信通知」的正解

探测结果：
- `usernotifications/unnotificationattachment` ✅ iOS10.0+（通知附件，**属于自己 App 的通知**）
- `usernotifications/notificationcontentextension` ❌ 404
- `usernotifications/unnotificationextension` ❌ 404

⚠️ **这批 404 需要谨慎解读** —— `UNNotificationServiceExtension` / `UNNotificationContentExtension`
是**真实存在的**公开 API（iOS 10+），只是 DocC 索引路径可能不是这个拼法。
**我们标注为「路径未命中，需进一步核实」，不写成「不存在」。**

**但即便核实为「存在」，它也帮不上忙**，原因是它的工作方式：
> Notification Content Extension 只能处理**你自己 App 投递的通知**，
> 不能拦截其它 App（Mail / Messages）的通知。

⇒ **这是一个关键的架构分界**（见第 3 节）：想在 Mail/短信通知发生时抓到内容，
用户必须**先把那个通知转发/共享到我们的 App**，或者我们只能做**不依赖通知内容**的通用提醒。

### 2.5 App Intents / 快捷指令 —— ✅ 官方「用户主动投递」通道，iOS16+

| 探测目标 | 结果 |
|---|---|
| `appintents` | ✅ iOS16.0+ / watchOS9.0+ |
| `appintents/appintent` | ✅ 可被 Siri / 快捷指令 / Spotlight / 小组件调用 |
| `appintents/appentity` | ✅ 自定义实体类型，可被系统索引与检索 |
| `appintents/entityquery` | ✅ 按标识定位实体实例 |
| `coreSpotlight` | ✅ iOS9.0+，`CSSearchableItem` / `CSSearchableIndexDelegate` |

**这才是「用户授权读取邮件」在 iOS 上真正可行的形态**：
用户用**快捷指令**或 **Siri** 把一封邮件的正文/要点传给我们的 App
（`AppIntent` 接参数），或用户用**分享菜单**把邮件文本分享给我们。

## 3. 混合架构设计（基于上面取证后的可行形态）

### 3.1 架构总览：四层事件源

```
┌─────────────────────────────────────────────────────────┐
│  L0  系统事件（无需授权或极简授权）                      │
│  • CXCallObserver：来电/去电/挂断（含时长）              │
│  • BGTaskScheduler / BGProcessingTask                   │
│  • 日历 / 提醒事项（EventKit，只读）                     │
└───────────────┬─────────────────────────────────────────┘
                │  LifeEvent
┌───────────────▼─────────────────────────────────────────┐
│  L1  麦克风事件驱动录音（用户明确授权 + 持续指示）        │
│  • 通话期间：CallKit 事件驱动，而非全天                  │
│  • 会议/面对面：手动一键开启，事件结束自动停             │
└───────────────┬─────────────────────────────────────────┘
                │
┌───────────────▼─────────────────────────────────────────┐
│  L2  用户主动投递（App Intents / 分享菜单 / 快捷指令）    │
│  • 邮件要点 → 快捷指令或分享菜单                          │
│  • 短信要点 → 分享菜单                                   │
│  • 语音转文字 → 分享菜单 / 听写                          │
└───────────────┬─────────────────────────────────────────┘
                │  LifeEvent
┌───────────────▼─────────────────────────────────────────┐
│  L3  提醒生成层（沿用现有已实现代码，零改动）             │
│  LifeEvent → ReminderCandidate → 用户确认 → EventKit    │
│  （误报防护：无显式指令词 / 置信度<0.85 / 过期 / 临近    │
│    / 每日重复例外 / 同刻同动作去重）                      │
└─────────────────────────────────────────────────────────┘
```

### 3.2 ★ 四个关键设计决策

**决策 1：L1 从「全天录音」改为「事件驱动录音」**
不是全天，而是：
- **通话窗口**（`CXCallObserver` 观察到接通 → 开录；挂断 → 停录）
- **用户一键开启的对话窗口**（手动/自动检测，事件结束自动停）
- 录音**指示**必须持续可见（Guideline 2.5.14）

**决策 2：L2 走「用户主动投递」，而不是「App 自行读取」**
这在 iOS 上是**唯一合规且能上架**的形态，而且它有个被忽视的优点：
> **用户主动投递 = 用户已经读过、已经筛选过、已经决定「这件事值得记」**。
> 这直接解决了全天录音模式最大的质量难题 —— 从 8 小时噪音里挑出那 1 条有价值的时间表达。

**决策 3：L0 的 CallKit 通话事件，本身就是「生活节点」的高质量来源**
「妈妈打来电话，我跟她说了三点半要去接孩子」——
**通话事件给出「这件事是重要的」，通话录音给出「具体内容」**。
两者结合，误报率天然低于全天录音。

**决策 4：L3 提醒生成层完全复用，不动一行代码**
现在的 `ReminderCandidate` 逻辑（132/0 测试全绿）本来就是**与录音来源无关**的 ——
它吃的是 `LifeEvent`。换源不改下游。

## 4. 功耗与存储：您最关心的点

### 4.1 推理（**合理推断**，非实测 —— 真机压测仍未做）

| 方案 | 麦克风开启时长 | 日均音频 | 存储（60s 段，压缩后约 8 KB/段） |
|---|---|---|---|
| 全天录音（现状设想） | **24 h** | 1,440 段/天 | ~11.5 MB/天 |
| 事件驱动混合 | **估 1–3 h/天**（通话 + 会议/对话窗口） | 60–180 段/天 | ~0.5–1.5 MB/天 |

⇒ **量级差异约 10 倍**，且**不再有「全天常驻麦克风」这一最敏感的隐私与审核点**。

### 4.2 一个必须诚实说明的反直觉点

**事件驱动模式不一定比全天模式省电。**

原因：
- 全天录音是**一次开启、持续运行** ⇒ 麦克风硬件持续工作，但调度开销固定
- 事件驱动是**多次开停** ⇒ 每次开停都有唤醒、权限检查、缓冲区初始化、指示器亮起的**固定开销**
  （尤其在 watchOS 上，App 唤醒本身就不便宜）

⇒ **真正的省电来源是「采集时长减少」，而不是「事件驱动」这个机制本身。**
如果事件驱动模式下用户一整天都开着对话窗口，它反而比全天模式更耗电。

**这一点我们不敢打包票，需要真机实测**（这正是 Gemini 第一轮就点出的「真机压测未做」缺口）。

## 5. 与全天录音方案对比

| 维度 | 全天录音 | 多源事件驱动（您的主张） |
|---|---|---|
| 采集时长 | 24 h | 估 1–3 h |
| 麦克风常驻 | 是 | **否** |
| 用户可理解性 | 「这 App 一直在录我」 | 「我授权了它读邮件/听通话」 |
| App Store 审核 | 2.5.14 持续指示，敏感 | **更友好**（无持续录音 = 少一条红线） |
| 价值密度 | 极低（8 h 噪音挑 1 条） | **高**（用户已筛选） |
| 覆盖广度 | 最广（所有对话） | 较窄但**含非语音信息**（邮件/短信 = 账单、预约、截止日） |
| 第三方同意 | 最难（全程都在录他人谈话） | **仍存在**（通话中他人说话） |
| 技术风险 | 高（后台保活 + 电量） | **低**（无后台保活依赖） |

### ★ 5.1 您这个方向真正赢在哪里（我们的判断）

**不是「更省电」，而是「价值密度更高 + 覆盖了非语音信息」。**

- 全天录音只能捕捉**说出来的话**。您提的邮件/短信能捕捉**账单缴费日、预约时间、付款截止、家人提醒** ——
  这些是**健忘者/认知衰退老人最需要的东西**，而他们**从来不会说出来**（因为写下来那一刻就已经「想起来了」，
  而「想起来」正是他们失败的那一步）。
- ⇒ **全天录音和事件驱动不是替代关系，是覆盖不同盲区。**
  一个补「说过但忘了」，一个补「没说过但需要知道」。

### 5.2 但它引入了全天录音没有的新问题

| 新问题 | 说明 |
|---|---|
| **用户操作负担转移** | 用户要学会用快捷指令/分享菜单投递 ⇒ **又变成「要用户主动做点什么」**，而这正是我们要解决的痛点本身！ |
| **覆盖不连续** | 用户不分享、不开会、不接电话 ⇒ 那天什么都没抓到 |
| **第三方同意更复杂** | 邮件是对方写的，短信是对方写的，通话是对方说的 —— **用户授权 ≠ 对方同意** |
| **投递质量差异大** | 用户随手分享一段无关内容 ⇒ 抽取质量下降 |

★ **这是我们目前看到的最大风险，需要 Gemini 重点判断**：您提的 L2 通道虽然合规，
但**它把「零操作」变成了「有操作」**，可能与产品的核心假设（无需主动设置）冲突。

## 6. 隐私、第三方同意与审核风险

| 风险 | 依据 | 缓解 |
|---|---|---|
| 第三方通信内容 | 5.1.2(i) 需明确披露 + 单独同意 | 隐私政策单列章节；**App 内不展示他人姓名以外的敏感内容**；提供「仅本机处理」开关 |
| 邮件/短信内容可能含医疗、金融信息 | 5.1.1(iii) 最小化 | **端侧处理，不上传**；本地索引可一键清除 |
| 通话录音 | 2.5.14 显式同意 + 可见指示 | 通话期间显示持续录音指示；提供「本次通话不录音」一键拒绝 |
| 越权读取尝试 | 2.5.1 只允许公开 API | **不做任何私有 API/越狱检测绕过** |
| 诱导同意 | 5.1.1(iv) 不得诱导 | 各通道**独立开关**，拒绝某通道不影响其它功能 |

## 7. 请 Gemini 论证 / 挑战的具体问题

1. **架构取舍**：全天录音 + 事件驱动混合，与纯事件驱动，您建议哪个作为主形态？
   我们的倾向是**混合**（各补盲区），但这会让产品复杂度上升。
2. **L2 的「用户主动投递」悖论**（第 5.2 节）：它是否让产品退回成「需要用户主动操作」，
   从而与「无需主动设置」的核心假设冲突？有无第三条路？
3. **电源 vs 隐私**：非持续录音在 App Store 审核与用户信任上是否**真的**是净收益？
   2.5.14 要求的是「recording 时有明确指示」，事件驱动只降低指示的持续时间，不消除义务。
4. **覆盖连续性**：纯事件驱动下，用户某天「什么都没发生」⇒ App 完全无产出 ⇒ 留存怎么办？
5. **第三方同意的工程解**：邮件/短信/通话中他人内容，App 内应如何显示与存储才算合规？
   我们倾向「只抽取动作与时刻，不保留原文」—— 这是否过于保守，会伤害可用性？
6. **L0 的 CallKit 通话事件**能否独立产生足够价值的提醒（如「通话 28 分钟 ⇒ 该跟进」）？
   这可能是**不需要录音、不需要授权**的最干净通道。
7. **优先级**：若只能做一条通道，您建议先做哪条？我们的排序是
   **L0 CallKit → L2 App Intents → L1 事件驱动录音**，理由是「合规风险递增」。
