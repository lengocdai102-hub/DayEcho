## 1. 🔴 P0-1：端侧转写 `SFSpeechRecognizer`

### 为什么必须第一个做

这是降级方案里**唯一**的硬缺口，也是「录音 → 文字」这条主路径的咽喉。
没有它，Watch 抓拍回来的一直是音频，用户得自己听一遍 ——
那就不叫「说一句就提醒」了。

> ★ **一个有价值的发现**：本机 SDK 的 Speech.framework **没有 `SpeechAnalyzer`**
> （`ls Headers | grep -i analyzer` → 无命中）。
> 那是 iOS 26 才引入的新端侧大模型框架。
> ⇒ 降级方案「砍掉端侧大模型依赖」在**当前 SDK 上本来就是唯一可行选项**，
> 不只是取舍问题 —— 用当前 SDK 写不了那条路。

### ⚠️ 关键技术坑：音频格式不匹配

`SFSpeechURLRecognitionRequest` 接受的容器/采样率**受限**：

| 项 | Watch 录的 | Speech 框架要 |
|---|---|---|
| 容器 | `.m4a`（MPEG-4/AAC） | **WAV / PCM** 或 CAF |
| 采样率 | **44100 Hz** | **16000 Hz**（16k） |
| 声道 | 1（单声道） | 1 |

⇒ **必须转码**：`.m4a` → 解码 AAC → 重采样 44100 → 16000 → 写 WAV → 喂 Speech。

实现选项：
1. `AVAudioConverter` + `AVAudioFile`（原生、可控、离线）
2. `AVAudioEngine` 手动 tap + 重采样
3. `ExtAudioFile` 直接读 m4a（更底层，代码量更大）

**建议选项 1**：直接用 `AVAudioFile(forReading:)` 读 m4a，`AVAudioConverter` 转 16kHz PCM，
用 `AVAudioFile(forWriting:)` 写 WAV。全部在本机可测（macOS SDK 也能编译这部分纯逻辑）。

### 强制离线的正确做法

```swift
let request = SFSpeechURLRecognitionRequest(url: wavURL)
request.requiresOnDeviceRecognition = true   // ★ 关键
request.shouldReportPartialResults = false   // 一次拿最终结果
request.addsPunctuation = true               // iOS 16+，对中文时间抽取很关键
```

⚠️ **`requiresOnDeviceRecognition = true` 的真实语义**：不是「强制离线」而是
「**不满足则直接失败**」。若设备/语言不支持端侧识别，任务会**报错**，而不是静默回落到云端。
⇒ 必须显式检查 `SFSpeechRecognizer.supportsOnDeviceRecognition`，
不支持时**明确报错给用户**，不能假装成功。

### ✅ 实现落点（P0-1 已完成）

| 层 | 文件 | 职责 |
|---|---|---|
| Kit | `AudioFormatProbe.swift` | 纯字节解析 ISO BMFF 头，取出采样率 / 声道 / 位深 / 时长 |
| Kit | `TranscriptionPlanner.swift` | 计划判定：直接识别 / 转码后识别 / 拒绝 + **面向用户的失败文案** |
| Kit | `TranscriptionResult.swift` | 结果模型 + 三态（成功 / 没听清 / 失败）+ 置信度闸门 |
| App | `AudioTranscoder.swift` | `AVAssetReader` 解码 AAC → **手写 RIFF/WAVE** 输出 16 kHz 单声道 PCM |
| App | `SpeechTranscriber.swift` | `SFSpeechRecognizer`，**强制 `requiresOnDeviceRecognition = true`** |
| App | `TranscriptionPipeline.swift` | 编排：探测 → 转码 → 转写 → 置信度闸门 → `IngestionPipeline` → 候选账本 |

**为什么判定逻辑全部下沉到 Kit 层**：
转写与转码是平台 API，本机可编译；但「该不该转」「失败时说什么」「这个结果能不能采信」
是产品决策，放在 Kit 层才能在本机单测覆盖每一条分支（不依赖 iOS SDK）。

**三条关键设计约束**：
1. **权限判定优先于格式判定** —— 权限是所有格式的先决条件，否则用户白折腾一轮。
2. **置信度闸门（0.35）** —— 「明天买菜」被听成「明天白莱」，规则层照样能抽出「明天」，
   生成一条看似正常但内容错误的提醒。对健忘者来说，**错的内容比没有提醒危害更大**。
3. **三态而非两态** —— 「抓拍了但没说话」是有效信息，不是错误 ⇒ 安静跳过，不弹错误。

**临时转码文件用完即删** —— 转码产物是原始录音的副本，不在磁盘上留第二份用户语音。

### 验收标准

- 飞行模式下，Watch 录完音传到 iPhone，**3 秒内**转出文字并挂上时间轴
- 转写结果经 `IngestionPipeline.ingest(text:source:.watchCapture)` 进入候选流
- 端侧不支持时**明确失败并提示**，不静默走云端
- 中文时间表达（「明天上午十点」「下周三」）能正确抽取

## 2. 🟠 P0-2：Watch→App 候选管线打通

### 为什么紧跟 P0-1

**改造前的实测调用链（基线 `8a4a62b`）**：

```
PhoneReceiveChannel.onSegmentVerified
    → 写入 RecordingStore（录音库）✓
    → NotificationCenter.post(.dayEchoSegmentsChanged)（通知刷新列表）✓
    → ✗ 从此没有任何东西进 IngestionPipeline
```

**改造后（已完成）**：

```
PhoneReceiveChannel.onSegmentVerified
    → 写入 RecordingStore（录音库）✓
    → 通知刷新列表 ✓
    → TranscriptionPipeline.process(segmentURL:segmentID:occurredAt:)  ★ 新增
        → AudioFormatProbe 探测格式（纯字节）
        → TranscriptionPlanner 判定（直接识别 / 转码 / 拒绝）
        → AudioTranscoder 转码（需要时）→ SpeechTranscriber 端侧识别
        → 置信度闸门（0.35）
    → IngestionPipeline.ingest(IngestedTextEntry(source:.watchCapture, audioRef:segment.id))
    → ledger.record(tiered)  ★ 候选进账本
    → NotificationCenter.post(.dayEchoCandidatesChanged)  ★ 确认列表刷新
```

`CandidateIngest` 只有两个入口：

| 入口 | 来源 | 调用点 |
|---|---|---|
| `ingestIncomingPayloads()` | Share / Intent 的**文本** | `DayEchoApp.swift:21`（启动时） |
| `ingestManualText()` | **手动录入** | UI 按钮 |

⇒ 改造前，**即使端侧转写做完了，转写结果也没有自动路径进入候选流** —— 还是得手动粘贴。

这两件事是**一个连续体**：P0-1 不做则 P0-2 无从验证。

### 好消息：下游能力已就位

| 能力 | 位置 | 状态 |
|---|---|---|
| 管线入口 | `IngestionPipeline.ingest(entry, now:)` / `ingest(text:source:)` | ✅ 已实现且可跑 |
| 分档路由 | `CandidateRouter`（`CandidateTier.swift:97`） | ✅ 已实现 |
| 信噪比分流 | `.watchCapture` 严格（须第一人称自我指令词）/ `.shareExtension`+`.shortcutIntent` 放宽 | ✅ 已实现 |
| 外部载荷落盘 | `IncomingPayloadStore`（`SharedContainer.swift:199`） | ✅ 已实现 |
| 账本接收 | `ledger.record(tiered)` | ✅ 已实现 |

**缺的只是把线接上** —— 已完成，接线点在 `DayEchoApp.swift` 的 `PhoneReceiverModel.transcribe(_:)`：
```swift
let tiered = IngestionPipeline().ingest(
    IngestedTextEntry(source: .watchCapture,
                      text: result.normalizedText,
                      occurredAt: segment.startedAt,
                      audioRef: segment.id.uuidString),
    now: segment.startedAt)
ledger.record(tiered)
```

### ✅ 工作量：小～中（已完成）

主要是**接线 + 状态管理**，不是写新逻辑：

1. ✅ 转写服务（`SpeechTranscriber`）产出文本
2. ✅ `PhoneReceiveChannel.onSegmentVerified` → 触发转写 → 转写完成 → 进管线
3. ✅ 转写失败**不静默丢音频** —— 音频已在校验通过的录音库里；
   `PhoneReceiverModel.transcriptionState` 暴露 `.failed(reason:)`，UI 可提示「转写失败」并重试
4. ✅ 转写与录音段 `id` 绑定（`IngestedTextEntry.audioRef` = `segment.id.uuidString`）

### 验收标准

- Watch 表盘抓拍 → iPhone 收到 → 自动转写 → **候选卡片出现在待确认流**，全程无需手动粘贴
- 转写失败时音频仍在、UI 有明确提示、用户可手动重试
- 转写文本的 `source == .watchCapture`，走**严格过滤**（不被 `.shareExtension` 的宽松规则误放行）

> ★ 免费账号无法使用 App Group ★

## 4. 🔵 P2：`ExtractReminderFromTextIntent`

### 为什么排最后

1. **target 方向不对**：`DayEchoIntents` 目前是 **watchOS** framework，
   降级方案要的是 **iOS 侧**快捷指令 ⇒ 需新建 iOS target
2. **价值未验证**：这个入口的价值取决于「你日常真的会去邮件/微信里选中一段话分享吗」
   如果主要场景是「当面听老板说话」，P1/P2 的价值都远低于 P0-1/P0-2
3. **但下游已齐**：`IngestionSource.shortcutIntent` ✓、`CandidateRouter` 放宽分档 ✓、
   `IncomingPayloadStore` ✓ —— 只差入口本身

### 一个技术优势

App Intent **可以不依赖 App Group**：
用 `openAppWhenRun = true` + 参数传递，或直接走 App Group（后者才有回退问题）。
⇒ **技术上不被付费账号卡住**（与 P1 不同）。

## 6. 已知风险与前置条件

| 风险 | 说明 | 缓解 |
|---|---|---|
| **端侧识别不可用** | `supportsOnDeviceRecognition == false` 的设备/语言组合 | 显式检查并明确报错，**不静默走云端** |
| **16kHz 转码开销** | 每段 120s 音频需解码+重采样 | 本机纯逻辑可测；转码在后台队列做 |
| **中文识别质量** | 端侧中文模型对口语时间表达的准确率未知 | 需真机实测；配合 `addsPunctuation` |
| **无 iOS SDK** | 本机仅有 Command Line Tools，`xcrun --show-sdk-path --sdk iphoneos` 返回空 | Speech 转码逻辑写成可在本机编译的纯 Swift 部分并单测；App 侧接线只能靠真机 |
| **EventKit 真机未验** | 阶段 3 的 312 项单测覆盖纯逻辑 | 见 `docs/上机前验证清单.md` 2.5 节 |

## 7. 与「先修第三轮缺陷」的关系

本文档排的是**新功能**。
第三轮审查发现的 3 条真缺陷是**已有闭环的正确性漏洞**：

| # | 缺陷 | 后果 |
|---|---|---|
| **A** | `.orphaned` 落盘失败后重启回 `.pending` | ⚠️ **可能重复写入系统提醒** |
| **B** | `.notFound` 无法区分「真没」/「查不到」 | 撤销时可能重演卡片 |
| **C** | 账本损坏后全量隔离、用户零感知 | 数据在，但用户不知道 |

⇒ **[A] 的严重度高于 P2**：
它会在**已完成的闭环**里产生用户从没要过的重复提醒 ——
对健忘者来说这是最坏的一类 bug（训练用户怀疑「系统又乱提醒我」）。

**建议顺序**：先修 [A][B][C] → 再做 P0-1 → 再做 P0-2 → P1/P2 待定。
